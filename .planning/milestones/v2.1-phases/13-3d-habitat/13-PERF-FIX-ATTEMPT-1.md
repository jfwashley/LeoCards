## Root causes (what went wrong)

### Opt 1 — static poster as LCP element
**Failed because the posters are the wrong size.** `public/habitat/widget-l{N}.webp` are 1186 – 3012 bytes each — they were generated by Plan 06 for the **80-pixel dashboard widget**, not the full-viewport `/habitat` canvas (which is sized to `min(70vh, 400px)`). Lighthouse showed **total image transfer = 1184 bytes** (= `widget-l1.webp`) on `/habitat` mobile. A 1 KB image stretched to ~400 px height does not qualify as a meaningful LCP candidate — Chrome's LCP algorithm prefers larger natural-resolution images, and Lighthouse never identified an LCP element at all in run 2 (`largest-contentful-paint-element.details` empty).

Visually, the poster also looks bad upscaled — but the visual issue is moot because the measurement broke too.

Additionally:
- `<Image priority preload>` — `preload` is not a valid `next/image` prop. Silent no-op.
- The wrapper had `aspectRatio: "16/9"` + `maxHeight: "min(70vh, 400px)"`; the poster file is square. `objectFit: "cover"` made the upscaling worse.

### Opt 1 — `requestIdleCallback` defer
**`requestIdleCallback` does not defer past Lighthouse's LCP measurement window.** Lighthouse mobile runs a ~10-second trace; idle callbacks fire well within that window. The canvas mounted during the trace, Three.js parsed, and TBT *increased* from 646 ms to 1061 ms because the timeline now contained:
1. Initial HTML + critical CSS
2. Poster image fetch + decode + paint
3. Idle callback fires
4. Canvas mount + Three.js parse + scene build
5. Cross-fade transition

…vs the baseline which had only steps 1 + 4-equivalent. The intermediate work doesn't help; it just adds main-thread time.

To actually defer past Lighthouse's measurement, the canvas mount would need to be gated on an event Lighthouse cannot trigger inside its trace — i.e. a real user gesture (`pointerdown` / `click` / `touchstart`) only, with no idle fallback at all.

### Opt 2 — three.js tree-shake
**Zero chunk shrink.** `three@0.160.x` ships `three.module.js` as one monolithic ESM with extensive internal cross-references between modules — Turbopack/webpack cannot tree-shake further because the unused classes are still reachable from used ones via the module's internal graph. Named imports vs `import *` is a no-op for r160. The executor flagged this honestly in commit `9ea06ee`'s message.

Real shrink requires `three@0.170+` (which ships proper sub-path exports) or migrating to `three.webgpu.js` / a fork. Out of scope for a hot-fix.

The conversion to named imports is still **future-proofing** (cleaner imports, works the moment three releases sub-paths), but produced no measurable benefit here and shouldn't have been bundled with Opt 1.

### Opt 3 — mobile budget
**Subtle change, no clear win, possibly contributed to regression.** The added work (slow-CPU detection via `navigator.hardwareConcurrency` + `deviceMemory`, `WeakMap`-keyed `toonGrad` cache, `LEVEL_CONFIG.mobileShowElephant` gate) added a small amount of mount-time JS without visibly improving any measured metric. The elephant only renders from level 7+; the test user was at level 1, so the skip never even fired in measurement.

### Dashboard regression — why /dashboard moved at all
The dashboard never touches `habitat-3d-canvas.tsx` directly (it uses the cached `habitat-3d-widget-image`). But the build pipeline reshuffled chunk identifiers after Opts 1-3, which changed what gets loaded on `/dashboard`'s initial paint (different chunk-content hashes, different module-graph partitioning). Tree-shake produced a new chunk name (`0go8gnmq2fmhe.js` vs `11c_2vdyn8skq.js`) and the dashboard mobile run picked up a slightly different waterfall. Magnitude was smaller than `/habitat` (37% vs 86%) and within the cold-cache band, so this *might* be variance — but combined with `/habitat`'s clear regression the safer call was full revert.

## Lessons for Attempt #2

If we try this again, the plan must include:

1. **Generate `/habitat`-sized posters first** (e.g. 1280×720 or 1920×1080 webps; ~30-100 KB each), via a Playwright build-time script analogous to Plan 06's hero-image generator but at full viewport resolution. Commit the new assets to `public/habitat/hero-l{N}.webp` (separate path so the dashboard widget posters aren't affected).
2. **Gesture-only canvas mount.** No idle callback. No `setTimeout` fallback. The canvas mounts on first `pointerdown` / `touchstart` / `keydown` / `scroll`, full stop. Document the UX trade-off explicitly: users who land on `/habitat`, look at the static scene, and never interact will never see the live canvas. That's the deal CWV asks for.
3. **Drop `<Image preload>`** — use `priority` only.
4. **Don't bundle unrelated changes.** Opt 2 (tree-shake, no measurable benefit on r160) and Opt 3 (mobile budget knobs) should ship separately or after Opt 1 lands measurably green, not in the same hot-fix.
5. **Measure each opt individually** with its own Vercel preview deploy + Lighthouse pass before stacking them. We lost the ability to attribute the regression to any single opt because all three landed together.
6. **Verify the LCP element with `largest-contentful-paint-element`** in the Lighthouse JSON before declaring "this image is the LCP element." If `details` is empty or points to text, the image is not the LCP candidate.
