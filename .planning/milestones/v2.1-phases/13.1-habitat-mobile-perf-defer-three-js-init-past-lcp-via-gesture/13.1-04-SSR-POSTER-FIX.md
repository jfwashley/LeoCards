# Phase 13.1-04: SSR Poster Fix

## Root-cause diagnosis

Lighthouse on Vercel preview `leocards-raczdfq76` reported `/habitat` mobile
LCP = 4717 ms with **"NO LCP DETAILS"** — meaning the trace recorded no
element claiming the LCP candidate role within the measurement window. The
network waterfall showed `hero-l{N}.webp` was never requested before LCP.

Two compounding bugs explain it:

1. **Wrong SSR boundary.** The `<Image src="hero-l{N}.webp" priority fill>`
   poster lived inside `src/components/habitat-3d-canvas.tsx`, which is
   loaded via `dynamic(() => import("@/components/habitat-3d-canvas"), { ssr: false })`
   in `habitat-scene.tsx`. The `ssr:false` boundary means **the entire
   subtree is absent from the SSR HTML**. The poster's `<img>`, and the
   `<link rel="preload" as="image">` Next.js injects from `priority`, were
   only emitted **after hydration** — long after the browser had already
   chosen an LCP element from whatever was visible at first paint (which
   was: nothing in that wrapper).

2. **Opacity-0 LCP disqualifier.** Even if the poster had moved up one
   level, it would still have been wrapped by
   `<motion.div initial={{ opacity: 0 }} animate={{ opacity: 1 }}>` in
   `habitat-scene.tsx` (lines 190-207 of the prior implementation). An
   element with opacity 0 at SSR time is excluded from LCP candidacy —
   browsers wait for the opacity-1 frame, which is now post-hydration and
   post-Lighthouse-window.

## Restructured boundaries

| Concern                                              | Lives in (was)                | Lives in (now)              |
| ---------------------------------------------------- | ----------------------------- | --------------------------- |
| Aspect-ratio sized outer wrapper                     | `habitat-3d-canvas.tsx`       | `habitat-scene.tsx` (SSR)   |
| SSR poster `<Image priority fill>`                   | `habitat-3d-canvas.tsx`       | `habitat-scene.tsx` (SSR)   |
| Level badge + mood indicator overlays                | `habitat-scene.tsx` (in motion.div opacity-0) | `habitat-scene.tsx` (outside motion.div, z-10) |
| `motion.div initial={{ opacity:0 }}`                 | wrapped poster + canvas       | **removed** (never wrapped the poster) |
| Gesture gate (`setupGestureGate`)                    | `habitat-3d-canvas.tsx`       | `habitat-3d-canvas.tsx`     |
| Hint timer + "Tap to animate" overlay                | `habitat-3d-canvas.tsx`       | `habitat-3d-canvas.tsx`     |
| Reduced-motion lockout                               | `habitat-3d-canvas.tsx`       | `habitat-3d-canvas.tsx`     |
| `mountHabitatScene` Three.js factory + dev hooks     | `habitat-3d-canvas.tsx`       | `habitat-3d-canvas.tsx`     |
| Poster cross-fade trigger                            | canvas internal (`canvasMounted`) | parent-owned (`canvasReady` state, set via new `onCanvasReady` prop) |

**Hint placement decision:** the "Tap to animate" hint stays in
`habitat-3d-canvas.tsx`. Rationale:
- It only appears 2 s after first paint, so SSR-visibility is irrelevant.
- Its dismiss-on-mount semantics are tightly coupled to `canvasMounted`,
  which the canvas component owns.
- Keeping it in the canvas file means H1–H8 unit tests need no boundary
  changes.

**`onCanvasReady` callback:** the canvas component invokes the optional
parent callback immediately after `mountHabitatScene()` returns (which sets
`data-ready="true"` synchronously). The parent flips `canvasReady` →
poster `opacity: 0` with a 200 ms ease-out. The poster's opacity is
**never 0 in SSR HTML** — `canvasReady` starts false on both server and
client.

## Why this should fix LCP

The browser now receives, in the initial document:

```html
<div class="w-full rounded-lg overflow-hidden" data-testid="habitat-scene-wrapper"
     style="aspect-ratio:16/9; max-height:min(70vh,400px); position:relative">
  <img src="/_next/image?url=%2Fhabitat%2Fhero-l{N}.webp..." alt="..." fill ... style="opacity:1">
</div>
```

…plus a `<link rel="preload" as="image" href="/_next/image?...hero-l{N}.webp">`
that Next.js injects into `<head>` because of the `priority` prop. The poster
is paint-visible at the first frame, opacity is 1, and the wrapper carries
intrinsic dimensions → the browser has an unambiguous LCP candidate well
before the gesture-gate fires and the Three.js chunk is fetched.

## Deviations / risk notes

- **`priority` is deprecated in Next.js 16** (`preload` is the new prop —
  see `node_modules/next/dist/docs/01-app/03-api-reference/02-components/image.md`
  line 291–293). It still works. A follow-up plan can migrate to `preload`;
  this fix intentionally minimises diff surface to prove the boundary
  hypothesis first.
- The canvas's outer wrapper changed `role="img"` + `aria-label` → these
  are no longer present because the parent's `<Image alt="...">` is the
  accessible representation. Reduced-motion users see only the poster
  (canvas returns `null`); their `<img alt="Tiger habitat level N">` is
  the AT-visible name.
- `HabitatLoadingSpinner` was deleted (was unused after switching the
  dynamic loading fallback to `() => null`). Rationale: the SSR poster
  fully covers the wrapper, so a spinner would visually fight the LCP
  candidate.
