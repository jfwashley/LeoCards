# Phase 13.1 Plan 01: Full-Resolution Habitat Poster Pipeline Summary

Built a one-shot `npm run posters:habitat` pipeline that drives Playwright to capture nine `/habitat` scenes at 1280x720 then sharp-encodes them to 20-100 KB webp LCP candidates at `public/habitat/hero-l{1..9}.webp`. Replaces the discarded 1-3 KB widget posters that Chrome refused to nominate as LCP (per `13-PERF-FIX-ATTEMPT-1.md`).

## Regenerate

```bash
# 1. Start dev server (NODE_ENV != production so window.__habitatSetTheta exists)
npm run dev

# 2. In a second shell, regenerate
npm run posters:habitat
```

Output is deterministic at fixed quality/effort — re-running produces byte-identical posters (sharp is deterministic at fixed quality/effort, theta is locked via `window.__habitatSetTheta(0)`, viewport is fixed).

## Deviations from Plan

### Rule 1 — bugfix during execution

**1. Canvas height clamp forces sharp upscale**

- **Found during:** Task 2 first execution.
- **Issue:** Plan asserts capture at 1280x720, but the wrapper `<div>` has `maxHeight: "min(70vh, 400px)"` (`habitat-3d-canvas.tsx:413`), so the canvas naturally renders at 1280x400 even when viewport is 1280x720. Initial dimension check failed: `L1: dimensions 1280x400 below 720x405`.
- **Fix:** Added a deterministic sharp `.resize(1280, 720, { fit: "fill", kernel: "lanczos3" })` step inside `encodeWebp()`. Upscaling stylised low-poly clay does not introduce visible aliasing, and the resize is part of the orchestrator (not the spec) so the on-disk PNG intermediate stays at canvas-native 1280x400.
- **Files modified:** `scripts/render-habitat-posters.mjs`
- **Commit:** `715698d`
- **Alternative considered:** Modify the wrapper's `maxHeight` to remove the 400px cap. Rejected — that's Plan 02's territory (`No changes to src/components/habitat-3d-canvas.tsx` is an explicit success criterion of this plan).

### Auth gate (expected flow, not a deviation)

- `/habitat` is under `(protected)`, so the spec calls `signUpWithDeck()` per the project's standard Playwright auth fixture. One transient Neon DB connection failure occurred mid-run; a retry succeeded on the next invocation.

### sharp dep declaration

- `sharp` is not explicitly listed in `package.json` devDependencies, but IS in `package-lock.json` (transitive via `lighthouse`, already in use by the legacy `e2e/scripts/render-hero-images.spec.ts`). Plan's threat-model entry T-13.1-SC predicted this is a no-op — confirmed. Did NOT add an explicit devDep entry because: (a) it's already locked, (b) adding it would expand the file list beyond plan frontmatter.
