# Phase 13.1-04 addendum — direct-CDN poster delivery

**Context.** After the SSR-poster-fix landed (commit `2045348` + `3601e29`),
Lighthouse mobile /habitat showed:

- LCP element correctly identified as the hero poster.
- Preload link emitted.
- Opacity 1 at SSR time, CLS = 0, desktop Perf 100.
- Mobile LCP samples: 2055 / 2138 / 3317 / 3329 / 4214 / 4339 ms (median 3329).

Variance (~2x) + the median sitting above the 2500 ms gate pointed at the image
delivery path, not at JS or layout. Investigation showed the poster was being
served through `/_next/image?url=%2Fhabitat%2Fhero-l1.webp&w=3840&q=75` — Vercel's
image-optimization Lambda. Cold-start of that Lambda adds ~100-300 ms to TTFB
for an asset that is already a correctly-sized, correctly-encoded ~25 KB webp.

## Opt A — `unoptimized` (committed)

**Change.** Added the `unoptimized` prop to the SSR `<Image>` in
`src/components/habitat-scene.tsx`.

**HTML emit before/after.** Confirmed by reading
`node_modules/next/dist/shared/lib/get-img-props.js` lines 96-123: under
`unoptimized`, `generateImgAttrs` returns `{ src, srcSet: undefined,
sizes: undefined }`. So:

- **Before:** `<img src="/_next/image?url=%2Fhabitat%2Fhero-l1.webp&w=3840&q=75"
  srcset="/_next/image?url=...&w=640 640w, ...&w=750 750w, ...&w=828 828w, ...">`
  plus a preload `<link as="image" href="/_next/image?...">`.
- **After:** `<img src="/habitat/hero-l1.webp">` plus preload
  `<link as="image" href="/habitat/hero-l1.webp">` (still emitted because
  `priority` is preserved). One byte-identical static-CDN fetch.

**Expected byte savings.** Zero — bytes were already ~25 KB. Latency savings
~100-300 ms (Lambda hop eliminated) per cold preview. This is exactly what
the variance pattern (cold vs warm Lambda) predicted.

**Commit.** `2c2461a perf(13.1-04): serve hero poster direct from CDN`.

## Opt B — narrow sizes + quality (skipped, documented)

The plan called for narrowing `sizes` and adding `quality={60}` to halve fetch
size to ≤ 20 KB. Under `unoptimized` neither prop has any effect:

- `sizes` is stripped from HTML emit (see source citation above).
- `quality` is irrelevant because no re-encode happens — the source webp is
  served as-is.

Achieving ≤ 20 KB would require **producing a smaller physical
`hero-l{N}.webp`** (re-encode the source PNGs at lower quality or smaller
target dimensions). That touches `public/habitat/*.webp`, which:

1. The current plan explicitly does NOT touch.
2. Would be a Rule 4 architectural deviation — new asset variants imply either
   regenerating from the master PNGs or accepting visible quality loss.
3. Likely diff-noisy against the Phase 13 Playwright screenshot baseline at
   `e2e/__screenshots__/habitat-states/`.

Recommended next plan: 13.1-05 to re-encode posters at q=60 / 720w-max (saves
~10-12 KB per poster) with paired snapshot regen, as its own auditable change.

## Deviations

- **Rule 4 — Opt B downgraded to documentation.** The mechanical changes
  prescribed (`sizes` narrowing, `quality={60}`) are no-ops in the `unoptimized`
  codepath that Opt A introduced. Achieving the ≤ 20 KB byte target requires
  producing smaller physical webp variants — architectural and out of scope
  for this plan. Surfaced as a recommended 13.1-05 plan rather than silently
  committing dead code.
