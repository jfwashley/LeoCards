## Issues Encountered

**`npx eas-cli@latest config --non-interactive` (the plan's literal verification command, zero extra flags) fails, despite the config being valid.**

Running the exact bare command from the plan's `<verification>`/`<acceptance_criteria>` blocks produces:
```
Input is required, but stdin is not readable. Failed to display prompt: Select build profile
    Error: config command failed.
```
exit code 1 — even though the installed CLI's own `--help` text for this command states the profile "Defaults to `production` if defined in eas.json." This reproduced identically across four independent variations (bare, `-p android` alone, `--json` alone, `-p ios --json`, and explicit stdin redirection from `/dev/null`), so it is not a transient npx/network hiccup.

To confirm this is a genuine `eas-cli@21.5.0` resolution-flow gap and not a problem with this plan's `eas.json` content, I validated all six explicit combinations instead:
```
eas config -e development -p android --non-interactive   -> exit 0
eas config -e development -p ios     --non-interactive   -> exit 0
eas config -e preview     -p android --non-interactive   -> exit 0
eas config -e preview     -p ios     --non-interactive   -> exit 0
eas config -e production  -p android --non-interactive   -> exit 0
eas config -e production  -p ios     --non-interactive   -> exit 0
```
Every one exits 0 and prints a fully-resolved, valid configuration (confirmed the `production`/`android` case's full JSON output: `credentialsSource: "remote"`, `distribution: "store"`). This proves `mobile/eas.json`'s content is completely valid and CLI-accepted; the bare, flag-less invocation is an upstream CLI quirk where the documented "defaults to production" behavior does not actually trigger under `--non-interactive` when neither `-e` nor `-p` is supplied (plausibly related to `app.json`'s auto-populated `platforms: ["ios","android","web"]` array, since EAS Build has no concept of a "web" build profile to resolve against). Flagging for any future executor or verifier who re-runs this exact literal command on this CLI version: use explicit `-e`/`-p` flags — the bare non-interactive form cannot be trusted here.

**`eas init` added an `owner` field beyond the plan's anticipated "project ID only" diff.** The plan's `<interfaces>` text anticipated "the only structural addition is the EAS project ID," but `eas init --account jfwashley` also wrote `"owner": "jfwashley"` into `mobile/app.json`. This is expected, CLI-driven behaviour (not a manual addition) — necessary so that every future `eas` command (build, submit, update) resolves unambiguously to the correct account without requiring `--account` on every invocation, given this Expo account has access to two organizations. Confirmed via `git diff` that no other unexpected keys were added.
