**Auth client shape (RESEARCH Pattern 2, verified against the downloaded package source — not just
docs).** `createAuthClient` from `better-auth/react`, with `baseURL` set from `mobile/lib/config.ts`'s
`API_BASE_URL`, and one plugin: `expoClient({ scheme: "leocards", storagePrefix: "leocards", storage:
SecureStore })` where `SecureStore` is the whole `expo-secure-store` module namespace. That module
genuinely exports synchronous `getItem`/`setItem` alongside the async pair, which is exactly the
interface `expoClient`'s storage adapter expects — RESEARCH verified this from the package's own
`.d.ts` after an initial web summary contradicted itself.

`scheme: "leocards"` must agree with `mobile/app.json`'s existing scheme and with the server's
`trustedOrigins` entry added in plan 28.2-03. All three are the same string; if any one drifts, native
auth requests are rejected on origin grounds.

**The session split (NAT-03's core requirement).** The web's `src/lib/auth-session.ts` exposes
`getSession()` (cached, cookie-cache-served) and `getSessionFresh()` (passes
`query: { disableCookieCache: true }`, forcing a live DB read so a just-revoked session is never
treated as valid — D-04, 27-01). The native mirror is the same distinction on the client:
`authClient.getSession()` for ordinary reads, and a `getSessionFresh` export that passes
`{ query: { disableCookieCache: true } }`. `disableCookieCache` is confirmed present on the installed
better-auth client's `SessionQueryParams` type. The server-side precedent for a revocation-sensitive
read is `src/app/api/account/route.ts`, which already ships this exact flag.

**Auth client method names carry over 1:1** (28.2-PATTERNS.md §Shared Patterns, sourced from five web
call sites): `authClient.signUp.email({ email, password, name })`,
`authClient.signIn.email({ email, password })`, `authClient.requestPasswordReset({ email, redirectTo })`,
`authClient.signOut()`. All return `{ data, error }` and the universal web convention is
`if (error) { setSomeError("…"); return; }` — never throw. Preserve that shape natively.

**Field rules and error copy** (28.2-UI-SPEC.md §Copywriting Contract — these strings are the contract,
not suggestions):

| Schema | Field | Rule | Message |
|---|---|---|---|
| signup | name | required, non-empty | `Name is required` |
| signup | email | valid email | `Please enter a valid email` |
| signup | password | at least 8 characters | `Password must be at least 8 characters` |
| signup | nativeLanguage | one of the app's languages, defaults to English | (no message — always valid, cannot be empty) |
| login | email | valid email | `Please enter a valid email` |
| login | password | required, non-empty | `Password is required` |
| forgot | email | valid email | `Please enter a valid email` |

D-22 requires the native signup payload to include `nativeLanguage`, which the WEB signup form does
not collect — `src/app/(auth)/__tests__/signup-payload.test.tsx` asserts its absence from the web
payload. The language set is en/fr/es only; read the canonical labels from `LANGUAGE_LABELS` in
`src/lib/core/decks.ts` and the option list in `src/components/welcome/welcome-step-choose.tsx` rather
than inventing them. Default is `en`, matching both the web welcome flow and better-auth's
`additionalFields.nativeLanguage.defaultValue`.

**D-24 notice copy, verbatim** (28.2-UI-SPEC.md §10.5, locked from CONTEXT §Specifics — do not
reword): `You've been signed out — please sign in again.`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app process → OS keychain | The session token crosses into iOS Keychain / Android Keystore via the Expo plugin's storage adapter |
| device → backend | Every credential and session request leaves the device over the network to the configured base URL |
| better-auth cookie cache → authorisation decision | A cached session up to 5 minutes stale can be served unless a read explicitly opts out |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28.2-19 | Elevation of Privilege | Session freshness | mitigate | `getSessionFresh` passes `disableCookieCache: true`, with a unit test asserting BOTH that the fresh read sets it and that the ordinary read does not. This is RESEARCH's "stale/revoked session still accepted on a device" pattern and NAT-03's stated requirement |
| T-28.2-20 | Information Disclosure | Session token at rest | mitigate | Persistence delegated entirely to `expoClient`'s SecureStore adapter (OS Keychain/Keystore); no hand-rolled storage, asserted by a grep for cookie/chunk handling. RESEARCH verified the adapter already chunks >1800-character values and normalises colon-unsafe keys — a competing layer would corrupt it |
| T-28.2-21 | Information Disclosure | Console output | mitigate | No logging anywhere in the auth client, asserted by a grep. React Native console output has no redaction layer, and tokens/passwords would otherwise be visible in Metro logs |
| T-28.2-22 | Spoofing | `scheme` / origin agreement | mitigate | Acceptance criteria require the `leocards` scheme string to match across `mobile/app.json`, `mobile/lib/auth-client.ts` and the server's `trustedOrigins`. Drift in any one silently breaks origin trust (RESEARCH Pitfall 8) |
| T-28.2-23 | Information Disclosure | Login error copy | mitigate | Login's schema requires only a non-empty password, deliberately not the 8-character policy — mirroring the shipped web behaviour so the form does not leak password policy to an unauthenticated caller |
</threat_model>
