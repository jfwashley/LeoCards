Target state (RESEARCH Pattern 1 / PATTERNS Group H) — exactly three changes:
1. A new import: `import { expo } from "@better-auth/expo";`
2. A new top-level `trustedOrigins` array containing the literal `"leocards://"` plus, only when
   `process.env.NODE_ENV === "development"`, the dev wildcards `"exp://"`, `"exp://**"` and
   `"exp://192.168.*.*:*/**"`.
3. `plugins: [nextCookies()]` becomes `plugins: [expo(), nextCookies()]`.

Everything else in the file stays byte-identical: the `drizzleAdapter` full-schema call, the
`nativeLanguage` additionalField (D-22 needs no new server work — the field already exists),
`sendResetPassword`'s Resend callback, `revokeSessionsOnPasswordReset: true`, and the
`session.cookieCache` block with its 300s TTL (27-01 / D-03).

Why the origin trust matters mechanically (RESEARCH, verified from the downloaded package source):
the native client sends `"expo-origin": Linking.createURL("", { scheme: "leocards" })` — roughly
`"leocards:///"` — and the server plugin's `onRequest` hook copies that header into the standard
`origin` header when no browser Origin is present, so the existing trust logic evaluates it. The
auto-added `"exp://"` entry does not match `leocards://`, and the D-36 prod-proof run is not
`NODE_ENV=development`. Both facts make the explicit `leocards://` entry load-bearing.

Regression baselines to re-establish (do not assume): `npx tsc --noEmit` clean; `npx vitest run` at
or above the 28.2-01 post-bump count with the four documented flakes re-checked in isolation
(`deck-switcher`, `image-upload-flow-extract-errors`, `review-list-commit-guard`, `cooldown-config`);
`npm run build` clean with all 12 native-v1 routes present.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| native client → `/api/auth/[...all]` | Untrusted device sends a self-declared `expo-origin` header that the server promotes to `origin` for trust evaluation |
| developer machine → production | A push to `main` auto-deploys the auth core; there is no staging gate between them |
| browser client → `/api/auth/[...all]` | The existing web surface must keep working unchanged across this edit |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28.2-06 | Spoofing | `trustedOrigins` in `src/lib/auth.ts` | mitigate | Trust exactly the literal `"leocards://"` in all environments; keep every `exp://` wildcard inside the `NODE_ENV === "development"` branch, asserted by an acceptance-criteria node check. A wildcard trusted in production would let any `exp://…` origin pass the CSRF/origin check |
| T-28.2-07 | Tampering | better-auth plugin ordering | mitigate | Acceptance criteria parse the plugins array and assert `expo()` is first and `nextCookies()` is last. Wrong order silently breaks cookie writes on native sign-in/sign-up responses (RESEARCH Pitfall 2) |
| T-28.2-08 | Denial of Service (availability of the live web app) | Every existing web auth flow | mitigate | Full regression (`tsc`, `vitest run`, `npm run build`, scoped biome, `qa:run`) before the push; blocking human authorisation on the push itself; three-way post-deploy verification; `perf:recert` afterwards |
| T-28.2-09 | Elevation of Privilege | `session.cookieCache` / `revokeSessionsOnPasswordReset` semantics | mitigate | Acceptance criteria require `git diff` to show those blocks byte-unchanged. The plugin addition must not perturb the 27-01/D-03 revocation semantics that NAT-03 depends on |
</threat_model>
