<planner_decisions>
- **No `@/` path alias inside `mobile/` — use relative imports everywhere.** Two concrete reasons.
  (1) The repo's `vitest.config.ts` aliases `@` to the WEB app's `./src`, so any mobile test importing
  through `@/` would silently resolve into the Next.js tree. (2) Metro's tsconfig-paths support is an
  Expo experiment flag, i.e. one more thing that can differ between `tsc` and the bundler. The mobile
  tree is three directories deep; relative imports cost nothing and remove both risks.
- **`experiments.typedRoutes` stays OFF this phase.** It generates `.expo/types/router.d.ts` at
  dev-server start, which would make `npx tsc --noEmit --project mobile/tsconfig.json` — the automated
  gate every mobile plan leans on — depend on a generated artefact that is gitignored. Not worth it
  for a shell with eight routes.
- **The theme module is a plain TS constant object, not a React context or a styling library.** D-31
  asks for TS constants; RN's `StyleSheet.create` consumes them directly. Adding a theming runtime
  would be inventing a problem.
- **`config.ts` derives the web origin from the API base URL rather than taking a second env var.**
  The API and the web app are the same Vercel deployment, so one value cannot drift from the other —
  and the password-reset `redirectTo` (D-21, plan 28.2-10) then cannot be pointed anywhere a caller
  chooses. That is the open-redirect mitigation, made structural.
- **`mobile/index.ts` is deleted, not edited.** expo-router owns the entry point via
  `"main": "expo-router/entry"`; a second registerRootComponent entry would be dead code. Its job
  (proving Metro cross-workspace resolution) is already done and recorded in 28.1-08.
</planner_decisions>
