## Design System

| Property | Value |
|----------|-------|
| Tool | **none** — shadcn is a web-only registry (Radix UI primitives over the DOM); it categorically cannot run on React Native. The repo's root `components.json` governs only `src/` (the Next.js web app) and has zero applicability to `mobile/`. This is a technical fact, not a declined option — the shadcn gate is not applicable to this phase. |
| Preset | not applicable |
| Component library | None. 100% hand-built RN components mirroring the web's own 100% hand-built Daybreak atoms (`src/components/daybreak/*` uses zero shadcn/Radix components either — `TField`/`TBtn`/`Card`/`Pill` are all plain styled elements). Faithful continuation of that pattern on native. |
| Icon library | **None new.** Every glyph in this phase's scope is a hand-drawn flat-geometric shape (matching the web's explicit "no emoji" convention, 25-UI-SPEC precedent, and `h-back.tsx`'s own "no emoji, no SVG [DOM element]" comment) — built via `react-native-svg` (already required for D-30's Leo redraw) or plain `View`s with borders/border-radius, exactly like the web's `AccountGlyph`/`HBack` chevron. No `@expo/vector-icons` or other icon-font dependency is needed or recommended for this phase's scope. |
| Font | **Baloo 2** (`Baloo2_700Bold` only, in this phase's own call sites — see note below) — headings + brand wordmark. **Figtree** (`Figtree_400Regular` / `Figtree_600SemiBold` / `Figtree_700Bold`, all 3 genuinely used) — everything else. Loaded via `expo-font`'s `useFonts()` + `@expo-google-fonts/baloo-2` / `@expo-google-fonts/figtree`, per `28.2-RESEARCH.md` Pattern 5 (Expo Go runtime-only loading, D-34). |
| Status bar | `dark` content style (cream/white backgrounds throughout this phase's whole scope — auth, tabs, offline) |
| Splash screen | Reuse whatever default/placeholder Expo ships this phase — **do not design new splash artwork here.** Commissioned splash art is D-17/D-18, owned by Phase 28.5. `expo-splash-screen` is used only *functionally* in 28.2 (held during SecureStore session-restore to avoid a login-flash, per RESEARCH Pattern 5) — that's a behavioral use, not a design deliverable. |

**Note on Baloo 2 weight 600:** `28.2-RESEARCH.md`'s package list installs both `Baloo2_600SemiBold` and `Baloo2_700Bold` (a cross-phase package choice). Within **this phase's own screens**, every Baloo 2 call site (headings, brand wordmark) uses weight **700 only** — confirmed directly from `src/app/(auth)/*/page.tsx` (`font-display ... font-bold`) and `src/app/(auth)/layout.tsx`. Do not omit the 600 import (it matches the researched package), but do not invent a 600-weight Baloo 2 use case inside 28.2 either — none exists in the ported source.

## Native Rendering Notes (Web → RN Translation)

Concrete translations for the 3 CSS techniques the ported components use that have no 1:1 RN style prop (extends `28.2-RESEARCH.md` Pitfall 6 with exact numbers):

| Web CSS | RN Translation | Values |
|---------|-----------------|--------|
| Card shadow `0 12px 30px rgba(160,110,40,0.16)` | iOS: `shadowColor`/`shadowOffset`/`shadowOpacity`/`shadowRadius`. Android: `elevation`. | iOS: `shadowColor:"#A06E28"`, `shadowOffset:{width:0,height:12}`, `shadowOpacity:0.16`, `shadowRadius:30`. Android: `elevation:10`. Tune visually against a web screenshot side-by-side — RN shadow rendering is not pixel-identical to CSS `box-shadow`, this is the starting contract, not a pass/fail pixel gate. |
| Button shadow `0 10px 22px rgba(242,138,31,0.30)` | Same pattern | iOS: `shadowColor:"#F28A1F"`, `shadowOffset:{width:0,height:10}`, `shadowOpacity:0.30`, `shadowRadius:22`. Android: `elevation:8`. |
| Scene background `linear-gradient(180deg, A 0%, B 100%)` | `expo-linear-gradient`'s `<LinearGradient>` | `colors={[A, B]}`, `start={{x:0,y:0}}`, `end={{x:0,y:1}}`, `style={StyleSheet.absoluteFill}` (or scene-sized) |

Render a second, larger, semi-transparent circle **behind** (rendered before, in JSX order) the solid sun circle, same center. | Sun circle stays 58×58 solid `#FFC95C`. ## Spacing Scale

**This phase's spacing values are ported verbatim from the shipped web Daybreak auth system** (`src/components/daybreak/auth-card.tsx`, `t-field.tsx`, `t-btn.tsx`, `src/app/(auth)/layout.tsx`), not re-derived from the generic 8-point default. This is the same documented approach `25-UI-SPEC.md` established for this project (its own Spacing Scale section: "multiples of 4, per the project's established scale" is itself a set of **inherited, ported values**, several of which are not literal 4-multiples — e.g. 18px, 15px). Daybreak's own design system (`design/handoff-daybreak/README.md` §Spacing) is explicit that its rhythm is **not** a strict 4-grid: *"Spacing rhythm: 14–20px between stacked blocks; 11–16px gaps inside groups; screen padding ~18–26px."* D-29's "faithful port, nothing new to invent" mandate means re-flowing these exact, already-shipped, already-approved values into a generic 4-grid would be a **deviation**, not a correction.

| Token | Value | Usage in This Phase |
|-------|-------|----------------------|
| Screen h-padding | 26 | Auth shell + offline screen horizontal padding (`px-[26px]`) |
| Screen v-padding | 40 | Auth shell vertical padding (`py-10`) |
| Page column gap | 20 | Brand row → card → cross-link stack (`gap-5`) |
| Brand row gap | 10 | LionFace-to-wordmark gap, both auth shell and tab header (`gap-2.5`) |
| Card content gap | 15 | AuthCard inner content stack, and every form's own field-to-field gap (`gap-[15px]`) — same 15 value 25-UI-SPEC already flagged as the cross-phase auth-form constant |
| Field internal gap | 6 | TField label→input→hint/error stack (`gap-1.5`) |
| Card padding | 20 top / 22 sides / 22 bottom | AuthCard content padding |
| Ghost-peek offsets | 0, 10 | The two peeking card-edge layers' `top` values |
| Header/tab-shell gap | 8–9 | Brand-cluster icon-to-text gap (8); header right-cluster gap (9, matches `app-header.tsx`'s existing value) |
| Teaser stack gap | 16, 8 | LionFace→heading (16), heading→line (8) — net-new, chosen to sit inside the README's documented 11–16/14–20 rhythm bands |
| Offline stack gap | 20, 8, 24 | Glow+Leo→heading (20), heading→body (8), body→button (24) — net-new, same rhythm-band discipline |
| Touch-target floor | 44 | Hard floor for every interactive control (glyph buttons, sheet row, tab items) — see §Accessibility Contract |

**Control-height exceptions (inherited, not new tokens — ported verbatim):**
- `TField` height: 48 (`h-12`)
- `TBtn` height: 50 (`h-[50px]`)
- Scene height: 216
- Card radius: 22 · Field radius: 12 · Button radius: 14
- Language-picker field: 48–52 (matches `TField`/welcome-select control height)
- Account sheet top-corner radius: 22 (matches card radius, sheet is visually a card sliding up)
- Offline/teaser glow circle: 140 diameter (net-new, sized to comfortably frame a 96/72pt LionFace)

**Source:** `src/components/daybreak/auth-card.tsx`, `t-field.tsx`, `t-btn.tsx`, `src/app/(auth)/layout.tsx`, `design/handoff-daybreak/README.md` §Spacing, radius, shadow, `25-UI-SPEC.md` Spacing Scale (precedent for how this project documents ported non-4-multiple values).

**Sign-off:** the non-4-grid exception above is accepted for Phase 28.2 on the same basis `25-UI-SPEC.md` already established for this shipped system — ported, already-approved production values take precedence over the generic 4-multiple default. This is a confirmed exception, not a provisional one; the checker should validate against the *ported-value* rule, not the generic 4-grid rule, for every token in this section.

## Typography

The established Daybreak system uses **3 body weights (400/600/700) + 1 display weight (700)** — this supersedes the generic "2 weights max" greenfield guideline, following the exact precedent `25-UI-SPEC.md` already set for this same shipped system ("Daybreak is an already-shipped, cross-phase-consistent system this phase must compose from, not re-scope"). All 4 weight/family combinations below are verified directly from the ported source files, not the README's summary (see the button-font correction note).

| Role | Size | Weight | Line Height | Used For |
|------|------|--------|-------------|----------|
| Display | 27 | 700 (Baloo 2) | 1.0 (`leading-none`, verified verbatim from `src/app/(auth)/layout.tsx`) | "LeoCards" brand wordmark — auth shell + tab-shell header |
| Heading | 22 | 700 (Baloo 2) | 1.2 | Screen/card headings: "Welcome back", "Create your account", "Reset your password", "Check your email", "You're offline", and (reused, not a bespoke size) every tab-teaser heading — see the resolved-into-core note below |
| Body | 14 | 400 (Figtree) regular · 700 (Figtree) bold for inline emphasis (cross-link anchor text, "resend") | 1.5 | Explainer copy, cross-link paragraph text, teaser lines, offline body copy, forgot-password sent-confirmation + resend copy |
| Label | 13 | 600 (Figtree) | 1.2 | Field labels, "Forgot password?" link, scene taglines, sheet row label |

**Sizes beyond the core 4 are a documented, precedented exception, not an unargued overflow.** Per D-29's faithful-port mandate, this phase reproduces the shipped web system's exact pixel values rather than force-fitting them into a smaller invented scale — the same justification already used above for the 3-weight system. `25-UI-SPEC.md` sets direct precedent for exceeding a generic size cap on this exact shipped Daybreak system: it declares **5** distinct sizes (22/17/15/13/12.5), explicitly framed as superseding the generic greenfield guideline because "Daybreak is an already-shipped, cross-phase-consistent system this phase must compose from, not re-scope." The 3 sizes below extend the core 4 for the same reason, each individually justified — no range values, no "matches surrounding" placeholders:

| Context | Size | Weight | Line Height | Justification |
|---------|------|--------|-------------|----------------|
| Field input value text (`TField`) | 15 | 400 (Figtree) | ~1.2 (single-line) | Ported verbatim from `t-field.tsx`'s `text-[15px]` input class — D-29 faithful port |
| Primary button label (`TBtn`) | 16 | 700 (Figtree — not Baloo 2, see button-font correction below) | 1 (vertically centered via flex, not literal leading) | Ported verbatim from `t-btn.tsx`'s `text-[16px] font-bold` button class — D-29 faithful port |
| Tab bar label | 12 | 600 (Figtree) | 1 | Net-new (D-25/D-26 — bottom tabs have no web analog; the web uses hub-and-spoke navigation), but not invented from nothing: grounded in Daybreak's own established micro-text/caption tier already proven elsewhere in this system (`src/components/daybreak/pill.tsx`'s 12px tag text; `25-UI-SPEC.md`'s 12.5px caption row) |

**Resolved into the core Body/Heading roles (no longer separate rows):**
- The forgot-password sent-confirmation paragraph, the resend line, and every cross-link's bold anchor segment ("Sign up" / "Sign in" / "resend") all render at Body's 14/1.5, using Body's 700-weight variant (see Body row above) for the bold portions — see §10.2/§10.3/§10.4 for exact placement. These previously carried their own ported sub-pixel values (14.5, 13) that are now intentionally flattened into the single Body size rather than preserved as separate near-duplicate entries.
- The tab-teaser heading (§10.7) reuses the Heading role (22/700) directly rather than a bespoke 20 — there is no rationale strong enough to invent a fifth headline size for a placeholder screen when Heading already exists and reads perfectly well at 72pt LionFace scale.

**Button-font correction:** `design/handoff-daybreak/README.md` describes Baloo 2 as covering "headings, level numbers, and buttons." The *shipped* `t-btn.tsx` source does **not** apply the `font-display` class — its button label renders in **Figtree 700**, not Baloo 2. Per D-29 ("the validated web design is the spec"), the shipped code is authoritative over the README's summary — port the button label as Figtree 700/16px, not Baloo 2.

**Source:** `src/app/(auth)/login/page.tsx`, `signup/page.tsx`, `forgot-password/page.tsx`, `layout.tsx`, `src/components/daybreak/t-field.tsx`, `t-btn.tsx`, `pill.tsx`, `design/handoff-daybreak/README.md` §Typography, `25-UI-SPEC.md` Typography (precedent for the "supersedes generic guideline" framing, both for weights and for sizes).

### 10.3 Signup

*Focal point: the amber "Create account" button, echoed by the same amber sun in the sunrise scene.*

```
AuthCard(scene: sunrise, tagline: "Your lion is waiting.")
  Heading (22/700 Baloo2): "Create your account"
  form, gap 15:
    TField "Name" — placeholder "Your name"
      error: "Name is required"
    TField "Email" — placeholder "you@example.com"
      error: "Please enter a valid email"  OR  "An account with this email already exists." (server)
    TField "Password" — placeholder "••••••••", secureTextEntry, hint "At least 8 characters"
      error: "Password must be at least 8 characters"
    LanguagePicker "I speak" — default "English", tap opens 3-row modal (English/French/Spanish)
      [net-new field beyond the web signup page — D-22 explicit requirement; see below]
    [generic-fallback error banner] "Couldn't create your account. Try again."
    TBtn "Create account"
Cross-link: "Already have an account? " + bold "Sign in"
```

**LanguagePicker detail (D-22, net-new — no 1:1 web-signup precedent; composed from `TField`'s shell + `welcome-step-choose.tsx`'s select/Chevron pattern, the closest existing analog for "pick one of {en,fr,es}"):**
- Label "I speak" — same Label style/weight as every other `TField` label (13/600) — a deliberate unification: the web's *only* existing "I speak" control (`welcome-step-choose.tsx`) uses 700/bold labels, but that's a different screen's own convention; unifying to `TField`'s established 600 keeps this signup form internally consistent (one label weight throughout), which is the tighter-scoped faithful-port target for *this* screen.
- Control: styled exactly like a `TField` input shell (48–52 height, radius 12, border 1.5 `#EDDFC9`, bg `#FFFBF4`), showing the selected label ("English") at 15/400, trailing chevron (9×9, rotated border-corner, `#B49B78` — identical technique to `welcome-step-choose.tsx`'s `Chevron`).
- Tap opens a modal list, title "I speak", 3 rows: English / French / Spanish (matches `ALL_LANGUAGES` in `src/components/welcome/welcome-step-choose.tsx` and `LANGUAGE_LABELS` in `src/lib/core/decks.ts` — en/fr/es only, no other languages exist in this app). Selected row: bg `#FFF1DC`, text `#B4762A` + trailing check glyph. Unselected: white bg, ink text. Tap a row → select + close.
- Default value: **English** (`en`) — matches both the web welcome flow's own default and better-auth's schema `defaultValue: "en"` (RESEARCH.md Pattern 1).
- No validation error state needed — always has a valid default, cannot be left empty.

### 10.4 Forgot Password

## Accessibility Contract

| Requirement | Implementation |
|-------------|-----------------|
| Touch targets ≥ 44 (dp/pt) | Hard floor for every interactive control — same numeric floor this project has enforced on web since Phase 23 (`e2e/10-mobile-responsive.spec.ts`'s `toBeGreaterThanOrEqual(44)`). Android's Material guideline (48dp) is a stricter secondary target where trivial to hit, not a requirement. |
| No automated RN touch-target test exists yet | `28.2-RESEARCH.md`'s Validation Architecture confirms the repo's `vitest` config is `environment:"node"` and cannot render RN components — the 44pt floor for this phase is verified via **D-33's manual device done-bar** (both platforms), not an automated assertion. Flagging the gap rather than implying a check that doesn't exist. |
| Small-Target Wrapper pattern | Header account glyph: 36×36 visual inside a 44×44 transparent hit area (identical technique + exact numbers to the web's `AccountNavButton`) |
| Naturally-compliant controls | `TField` (48), `TBtn` (50), language-picker field (48–52), account-sheet row (44+ via 20 padding + 16pt text) — no wrapper needed |

## Design Decisions Log

Discretion resolutions made during this UI-SPEC (auto mode — every item below was either unanswered by `28.2-CONTEXT.md`/`28.2-RESEARCH.md` or explicitly delegated to "Claude's Discretion"; each is a tasteful choice consistent with the shipped web Daybreak design, per the auto-mode instruction):

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Offline-screen visual design (D-32) | Reuse the auth scene's sun/glow motif at a calmer, full-screen scale, LionFace + heading + body + "Try again", no illustrated hills/grass | Full continuity with the established Daybreak visual language without over-building a whole new mini-scene for a utility screen; "Leo-branded" (D-30's cross-reuse mandate) is satisfied directly |
| Tab-teaser copy (D-28) | "Your words are gathering here soon." (Deck) / "Your next session is warming up here soon." (Study) / "Your habitat is growing here soon." (Habitat, Josh's own example, used verbatim) | Josh's own example sets the grammatical pattern ("Your {noun} is/are {verb-ing} here soon"); the other two mirror it for a consistent voice across all 3 teasers |
| Native-language picker UI (D-22) | Custom `TField`-shell button + tap-opens 3-row modal list (RN core `Modal`, no new picker library) | RN has no native `<select>`; a searchable/virtualized picker library is unjustified for exactly 3 static options — this is proportionate custom UI, not "hand-rolling a solved problem" |
| Native-language picker label weight | Unified to `TField`'s 600 (not the web welcome flow's 700) | Keeps the signup form internally consistent (one label weight throughout) rather than importing a different weight from an unrelated screen |
| Spinner component | RN's built-in `ActivityIndicator`, replacing web's `lucide-react` `Loader2` | Zero new icon-library dependency; platform-native spinner; matches the "Don't Hand-Roll" spirit without adding a dependency for one glyph |
| Tab bar icons | Hand-drawn flat-geometric `react-native-svg` shapes (stack/book/mound), not an icon-font library | Consistent with the web's own explicit "no emoji, no [icon-font]" convention (`AccountGlyph`, `HBack`); `react-native-svg` is already a required dependency for D-30, so this adds zero new packages |
| Button-label font (Typography correction) | Figtree 700/16, not Baloo 2, for `TBtn` | Verified directly from `t-btn.tsx` source, which has no `font-display` class — the README's general "Baloo 2 for buttons" claim doesn't match the shipped, authoritative code (D-29 makes shipped code the source of truth) |
| Forgot-password "sent" icon | Geometric envelope glyph (outline rect + flap line), not the web's literal "✉" emoji character | Matches this project's explicit "no emoji" convention (25-UI-SPEC, `h-back.tsx`) — the web's own use of an emoji character here is the one spot that convention wasn't applied; not carried forward to native |
| Account glyph accessibility label | "Account" (not web's "My Account") | This phase has no `/account` route yet (D-27 — that arrives in 28.5); "Account" describes what exists today without overclaiming a destination that doesn't exist yet |
| Sign-out color | Ink `#4A331C`, not destructive red, not amber | Mirrors the web's own `25-UI-SPEC.md` precedent exactly — sign-out is routine, not destructive; reserving red exclusively for validation errors keeps the destructive token meaningful |
| Spacing scale | Ported verbatim (15/22/26/etc.), not forced into a 4-multiple grid | D-29's "nothing new to invent" mandate + Daybreak's own documented non-4-grid rhythm (`design/handoff-daybreak/README.md`) + direct precedent in `25-UI-SPEC.md`'s own Spacing Scale section |
| `dusk` scene variant | Not ported this phase | No native screen uses it (D-21 keeps reset-password web-only) — porting unused code contradicts D-12-style "no gold-plating"; add later only if a native reset flow is ever built |
| Typography — teaser heading size | Reuse Heading role (22/700) instead of a bespoke 20 | Checker-directed fix: a 5th headline size for one placeholder screen wasn't justified; Heading already exists and reads well at teaser scale |
| Typography — confirmation/resend/cross-link sizing | Flattened into Body's 14/1.5 (with a 700-weight variant for bold segments), dropping the previously-separate 14.5/13/"matches surrounding" entries | Checker-directed fix: eliminates range values and unfixed placeholders; these were sub-2px variants of an already-declared role, not genuinely distinct sizes |
