<planner_decisions>
- **No native reset-password screen, and no deep-link handling.** D-21 is explicit: the emailed link
  opens the web reset page in the phone's system browser and never re-enters the app. The app needs no
  `Linking` call either — the mail client opens the browser. `revokeSessionsOnPasswordReset` on the
  server already handles session invalidation. Building a native completion flow is on the Deferred
  list; do not start one.
- **Signup does not navigate on success.** D-23 defers the first-visit welcome to 28.3, so a fresh
  native signup simply lands on the tab shell — which happens automatically once the session exists
  and plan 28.2-12's guard flips. Same reasoning as the login screen: an explicit navigation here
  would race the guard.
- **The language picker is a custom control, not a library.** React Native has no `<select>`, and
  three static options do not justify a searchable, virtualised picker dependency. 28.2-UI-SPEC.md
  §Design Decisions Log signs this off as proportionate custom UI rather than hand-rolling a solved
  problem — it is a `TField`-shaped button plus a `Modal` list.
- **The picker's options come from the schema's exported language list** (plan 28.2-07), not a second
  hardcoded array. One list means the control cannot offer an option the schema would reject.
- **Forgot-password always shows the sent state**, matching the shipped web page, which does not branch
  on the result. That is the anti-enumeration behaviour, and `auth-errors.ts` already encodes it: only
  a thrown/network failure produces a banner.
</planner_decisions>

**Forgot-password screen — port of `src/app/(auth)/forgot-password/page.tsx` (128 lines), per
28.2-UI-SPEC.md §10.4.** Default state: `AuthCard` with `DaybreakAuthScene variant="daylight"` and

`Enter your email and we'll send you a reset link.` in body/muted; one email field (testID
`forgot-email-field`); the generic error banner (testID `forgot-error-banner`); `TBtn` labelled
`Send reset link` (testID `forgot-submit-btn`).

Sent state replaces the form inside the same card (testID `forgot-sent-view`): heading
`Check your email`; a centred column with roughly a 12 gap containing a 52×52 circle in `#FFF1DC`
holding a small geometric envelope glyph — a flat rounded-rect outline plus a chevron "flap" line,
NOT the web's `✉` emoji character, because this project's no-emoji convention applies (the web page is
the one spot it was not applied, and it is not carried forward); then
`If an account exists, we've sent a reset link to ` with the address in body-bold ink and a full stop;
then `Didn't get it? Check spam, or ` with a tappable `resend` in body-bold `#C96F12` (testID
`forgot-resend-btn`) that returns to the default state, and a full stop.

input and never parameterised. The web equivalent uses `window.location.origin`, which has no native
counterpart.

**Shared mechanics** (identical to the login screen, plan 28.2-09): `useForm` + `zodResolver` over the
matching schema from `mobile/lib/auth-schemas.ts`; every field driven by `<Controller>` mapping
`field.onChange` to `onChangeText`, never `register()`; errors gated on `isSubmitted`; outcomes routed
through `mobile/lib/auth-errors.ts`; the button re-enabled in a `finally` block; no navigation on
success; no logging.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user → signup form | Untrusted registration input crosses to the backend, including a language code that becomes a stored user attribute |
| app → password-reset endpoint | The app supplies a `redirectTo` that determines where a password-reset email points |
| backend response → forgot-password UI | Any difference in what the screen shows for a known versus unknown email is an enumeration oracle |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28.2-31 | Tampering | `requestPasswordReset` `redirectTo` | mitigate | Passed the `PASSWORD_RESET_URL` constant from `mobile/lib/config.ts`, derived at build time from the configured base URL. Never built from user input, never a prop, never a parameter — asserted by criteria forbidding a template-built value. This closes RESEARCH's "open redirect via the password-reset redirectTo parameter" |
| T-28.2-32 | Information Disclosure | Forgot-password result handling | mitigate | The sent state renders whether or not the call reports an error, matching the shipped web page. Only a thrown/network failure differs, and that failure mode is identical for every address |
| T-28.2-33 | Information Disclosure | Signup email-taken message | accept | `An account with this email already exists.` is deliberately honest — the shipped web app made this exact trade (25-01 chose an honest message over better-auth's anti-enumeration masking). Signup enumeration is bounded by the existing rate limiting on the auth handler; this phase changes nothing about that decision |
| T-28.2-34 | Tampering | `nativeLanguage` input | mitigate | Constrained by the zod schema to the app's supported set (plan 28.2-07) and rendered from that same exported list, so the picker cannot offer a value the schema rejects. The server independently declares it as a typed `additionalField` |
| T-28.2-35 | Information Disclosure | Console / Metro logs | mitigate | No logging on either screen, asserted by grep |
</threat_model>
