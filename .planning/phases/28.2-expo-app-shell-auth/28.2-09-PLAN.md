<planner_decisions>
- **Login does NOT navigate after a successful sign-in.** The web pushes to `/dashboard`; native uses
  expo-router's declarative session guard instead (plan 28.2-12), so the route changes as a
  consequence of the session existing. Adding an explicit `router.replace` here as well would race the
  guard and produce a double navigation. This plan's screen ends at "the session now exists".
- **The web's `callbackUrl` open-redirect guard has no native equivalent to port** — there is no query
  string carrying a return path into a native login screen. The analogous native concern is the
  password-reset `redirectTo`, already closed structurally in `mobile/lib/config.ts` (plan 28.2-05).
  Do not invent a native `callbackUrl` mechanism.
- **Error mapping is extracted into a pure, tested module.** The rules are security-relevant (never
  enumerate accounts) and identical across three screens. Putting them in `auth-errors.ts` means the
  copy is asserted by a real test rather than by three separate greps, and plan 28.2-10 reuses them.
- **The auth shell adds keyboard handling that the web has no equivalent for.** A phone keyboard covers
  the lower half of the screen; a signup form with five controls will otherwise hide its own submit
  button. This is a native-platform necessity, not a design change.
- **`SignedOutNotice` is consumed on mount, once.** The notice module (plan 28.2-07) hands its value
  over exactly once, so navigating back to login later shows nothing — correct, because the message
  explains one specific transition.
</planner_decisions>

**Validation timing, ported exactly:** errors are shown only after the first submit attempt — the web
gates every `error` prop on react-hook-form's `isSubmitted`. Preserve that; validating on first
keystroke is a different, worse experience and a deviation from the approved contract.

**The `register()` gotcha (28.2-PATTERNS.md Group C, found by reading the real code):** react-hook-form's
`register()` returns a DOM-shaped `{ onChange, onBlur, name, ref }` object which does NOT wire up
against React Native's `TextInput` — `TextInput` emits `onChangeText(text)`, not a DOM event. Every
field must be driven by `<Controller>`, mapping `field.value` to `value`, `field.onChange` to
`onChangeText` and `field.onBlur` to `onBlur`. This applies everywhere the web source uses
`{...register(...)}`.

**Error-mapping rules (28.2-UI-SPEC.md §Copywriting Contract — exact strings):**

| Call | Outcome | Result |
|---|---|---|
| sign-in | any server error | field message `Incorrect email or password.` on the password field |
| sign-in | thrown / network failure | banner `Couldn't sign in. Try again.` |
| sign-up | any server error | field message `An account with this email already exists.` on the email field |
| sign-up | thrown / network failure | banner `Couldn't create your account. Try again.` |
| password reset | server error OR success | the sent-confirmation state either way (anti-enumeration — the shipped web page does not branch on the error) |
| password reset | thrown / network failure | banner `Couldn't send the reset link. Try again.` |

The single generic sign-in message is deliberate and load-bearing: it never reveals whether the email
exists. Do not add a "no account found" variant.

**Signed-out notice (28.2-UI-SPEC.md §10.5):** background `#FFF1DC`, radius 13, padding 12 vertical /
14 horizontal, centred text at the theme's label role in `#8A6235`, testID `signed-out-notice`. Copy
is locked verbatim in `mobile/lib/session-notice.ts` — render that constant, never a retyped string.

**Error banner (28.2-UI-SPEC.md §Color):** background `#FCEBE6`, border `#F2C9BF`, ink text, radius and
padding matching the notice. Shared by all three auth screens; plan 28.2-10 imports it.

**Test constraints:** the root `vitest.config.ts` aliases `@` to the WEB app's `./src`, so mobile tests
must import relatively. `auth-errors.ts` must import nothing from `react`, `react-native` or `expo-*`
so the node environment can load it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user → login form | Untrusted credentials are collected here and sent to the backend |
| backend error response → rendered copy | A server-supplied message must never reach the screen verbatim |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28.2-26 | Information Disclosure | Sign-in failure copy | mitigate | `auth-errors.ts` maps every server error to the single message `Incorrect email or password.`, with a dedicated test asserting that even a server error naming a missing user produces that same string. No account-enumeration oracle |
| T-28.2-27 | Information Disclosure | Client-side validation strictness | mitigate | The login schema requires only a non-empty password (plan 28.2-07), so the form does not advertise the password policy to an unauthenticated caller |
| T-28.2-28 | Information Disclosure | Console / Metro logs | mitigate | No logging on the screen, asserted by grep. React Native console output is unredacted and visible to anyone with the Metro terminal |
| T-28.2-29 | Denial of Service (double submission) | Sign-in button | mitigate | `TBtn`'s combined pending/disabled condition (plan 28.2-06) drives the real disabled prop, and the handler re-enables only in `finally` |
| T-28.2-30 | Spoofing | User confusion after a silent bounce | mitigate | D-24's signed-out notice explains the transition in the app's own voice, so a revoked session never presents as an unexplained login prompt — the state a phishing lookalike relies on |
</threat_model>
