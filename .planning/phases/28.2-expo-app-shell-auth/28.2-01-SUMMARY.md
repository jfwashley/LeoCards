## Decisions Made

1. **ERESOLVE #1 (initial single-command install):** `npm install --save-exact better-auth@1.6.26 @better-auth/expo@1.6.26` failed because the on-disk tree still had `better-auth@1.5.6`'s own sub-adapter family (`@better-auth/drizzle-adapter@1.5.6`, `@better-auth/kysely-adapter@1.5.6`, etc.) peer-requiring `@better-auth/core@"1.5.6"` exactly, conflicting with `@better-auth/expo@1.6.26`'s peer requirement of `@better-auth/core@"^1.6.26"`. Confirmed via `npm view better-auth@1.6.26 dependencies` that the *target* graph is internally consistent (every sub-adapter pinned to `1.6.26` in lockstep) — this was npm's incremental resolver struggling against stale on-disk state, not an unsatisfiable request. Stopped per the plan's explicit instruction rather than adding `--force`/`--legacy-peer-deps`, and returned a checkpoint.

2. **ERESOLVE #2 (Step A):** Adding `@better-auth/core@1.6.26` explicitly to the same install command surfaced a *deeper* conflict one level down (`@better-auth/core@1.6.26` peer-requires `better-call@"1.3.7"` exactly; the old `better-call@1.3.2` from the 1.5.6 tree was still on disk). This confirmed the same root cause at a different layer — incremental resolution against a partially-stale tree — reinforcing that a clean-slate approach (Step B) was the right escalation, not a third incremental patch attempt.

3. **Step B executed cleanly:** deleting `package-lock.json`, `node_modules/`, and the nested `mobile/node_modules/` (react version differs from root, so it has its own nested copy), then editing `package.json` directly to the two exact target versions and running a from-scratch `npm install`, resolved with zero errors and zero override flags.

4. **Lockfile-drift audit:** Wrote a small Node script to diff the old (`git show HEAD:package-lock.json`) and new `packages` maps by path and version. Outside the better-auth family: 158 added / 200 removed / 268 changed entries; total package count actually *decreased* (1292 -> 1251 at that point in the process). Critically: **zero direct `package.json` dependency crossed its own already-declared semver range**, and **zero new top-level `package.json` entry appeared** beyond the two intended ones. The largest individual shifts (`@sentry/*` 9.x->10.x, `@opentelemetry/*` 1.x->2.x, `lucide-react` 1.0.1->1.28.0) are all several levels deep in third-party build/dev tooling (Expo's bundled telemetry, Lighthouse's puppeteer chain) or, for `lucide-react`, fully within its already-permissive `^1.0.1` range — none touch anything LeoCards imports directly or that sits near the auth surface. Judged this as ordinary churn from a lockfile that had not been fully regenerated in months, not the "extensive or suspicious" bar Josh set for a second stop — proceeded without an additional checkpoint.

5. **`npm ci` EBADPLATFORM:** the fresh lockfile's `node_modules/vitest/node_modules/@esbuild/aix-ppc64` entry was missing `"optional": true` (carrying `"extraneous": true` instead), unlike the *same* package correctly marked optional at two other lockfile paths (top-level and under `tsx`). This is a known class of npm arborist bookkeeping artifact from `npm install`'s incremental tree-building, not a real dependency problem, and unrelated to the better-auth peer question (already fully resolved by this point). Fixed with one additional idempotent `npm install` (zero arguments, zero flags) — the arborist self-corrected, removing the mismarked entry outright (`removed 15 packages`) — after which `npm ci` passed cleanly.
