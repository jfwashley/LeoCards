## Summary

The single most consequential finding this session: **`@better-auth/expo` (the official Expo integration) has a hard peer-dependency on `better-auth ^1.6.26`, but the repo has `better-auth@1.5.6` installed** `[VERIFIED: node_modules/better-auth/package.json, npm view]`. This is not a "nice to have" security bump — it is a mechanical requirement. `npm install @better-auth/expo` against the current lockfile will fail to resolve peers unless `better-auth` is bumped first. The good news: the specific CVE flagged by 28.1-09's `npm audit` (GHSA-qq9h-g4jm-xgf3, account-takeover class) only affects apps using the **magic-link or email-OTP plugins** `[CITED: GitHub Security Advisories]` — LeoCards uses plain `emailAndPassword` only, so the advisory does not currently apply to this app's actual attack surface. The bump is needed for the Expo plugin, not because the app is presently exploitable. This is exactly the checkpoint CONTEXT.md asked for: **surface it to Josh, do not silently bump.** No breaking changes were found in the 1.6.x line that touch `drizzleAdapter`, plugin ordering, `session.cookieCache`, `additionalFields`, `emailAndPassword.sendResetPassword`/`revokeSessionsOnPasswordReset`, or `nextCookies` `[CITED: GitHub releases, MEDIUM confidence]` — re-confirm by skimming the real CHANGELOG at execution time and running the full existing web regression suite immediately after the bump, before writing any native code.

For navigation, this research recommends **expo-router** over React Navigation (Claude's Discretion per CONTEXT.md). It ships as an Expo-SDK-bundled package (exact version pin, Expo Go-guaranteed), its current documented pattern (`<Stack.Protected guard={...}>`) maps directly onto the shell's auth-gating need, its own install list already requires `expo-linking`/`expo-constants` — which the better-auth Expo client needs unconditionally anyway — so choosing it adds no net new dependency surface over React Navigation, and its file-based route-group convention (`(auth)`/`(tabs)`) mirrors the web app's own Next.js App Router structure Josh already knows.

For session persistence, `expo-secure-store` genuinely exports both a sync (`getItem`/`setItem`) and async (`getItemAsync`/`setItemAsync`) pair `[VERIFIED: downloaded package .d.ts]` — the sync pair matches `expoClient()`'s expected storage interface exactly, confirming the official docs' `storage: SecureStore` one-liner is correct as written (this was independently verified from source, not assumed, after an initial web-summarisation genuinely conflicted with itself). The client plugin already chunks values over 1800 characters across sub-keys to work around the ~2KB native Keychain/Keystore ceiling — do not hand-roll this. For offline detection (D-32), recommend `@react-native-community/netinfo` (matches CONTEXT.md's own naming, Expo-Go-bundled at 12.0.1, purpose-built configurable reachability ping) over `expo-network`'s newer `useNetworkState`/`addNetworkStateListener` — though `expo-network` should still be installed since `@better-auth/expo`'s own internal online-manager silently degrades to "always online" without it.

For the Daybreak port, the exact web font weights (Figtree 400/600/700, Baloo 2 600/700), full colour token set, and the auth-flow reference implementation (signup/login/forgot-password field sets, validation, error copy, API calls) were all extracted directly from source and are reproduced below — this is a faithful-port phase, not a from-scratch design phase.

**Primary recommendation:** Get Josh's explicit go/no-go on the better-auth 1.5.6→1.6.26 bump as an early, isolated, fully-regression-tested wave (server-only diff, before any native code lands) — the rest of the phase (expo-router shell, SecureStore session, NetInfo offline screen, Daybreak port) is comparatively low-risk and well-supported by official, Expo-Go-guaranteed tooling.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Sign up / sign in / sign out | Client (Expo/RN) | API/Backend (better-auth handler) | Client collects credentials + persists the resulting session; server validates and issues it |
| Session validation & revocation | API/Backend (better-auth server) | Database (Neon/Drizzle) | Server is sole source of truth for session validity; DB stores session rows (unchanged by this phase) |
| Session persistence across app launches | Client (SecureStore via `expoClient`) | — | Native Keychain/Keystore; no server role |
| CORS/origin trust for native requests | API/Backend (`expo()` plugin `trustedOrigins`) | — | Origin-header rewrite + trust-list evaluation happens server-side |
| Password-reset request | Client (native form, D-21) | API/Backend (better-auth + Resend) → Browser (web reset page) | Request originates native; completion happens entirely on web — no native tier involvement after the email is sent |
| Navigation shell / auth-gating | Client (expo-router `Stack.Protected`) | — | Pure client-side routing decision keyed on session presence |
| Offline detection & screen | Client (NetInfo) | — | Device-level connectivity signal; no server round trip needed |
| Daybreak theming / Leo art | Client (RN theme module + react-native-svg) | — | Static tokens + vector art, no backend involvement |
| EAS project link / build profiles | Build tooling (not a runtime tier) | — | `eas.json` / `extra.eas.projectId` are build-time config, inert at app runtime |

### Pattern 1: Server-side `expo()` plugin + `trustedOrigins`

**What:** Registers the Expo integration on the existing better-auth instance and declares which client origins are trusted.
**When to use:** Once, in `src/lib/auth.ts`.
**Example:**
```typescript
// Source: better-auth.com/docs/integrations/expo (official docs) + verified against
// downloaded @better-auth/expo@1.6.26 dist/index.js (server plugin auto-adds
// trustedOrigins:["exp://"] only when NODE_ENV==="development"; onRequest copies
// the client's "expo-origin" header into "origin" when no browser Origin is present)
import { betterAuth } from "better-auth";
import { drizzleAdapter } from "better-auth/adapters/drizzle";
import { nextCookies } from "better-auth/next-js";
import { expo } from "@better-auth/expo";
import { db } from "@/db";
import * as schema from "@/db/schema";
import { EMAIL_FROM } from "@/lib/account-constants";

export const auth = betterAuth({
  database: drizzleAdapter(db, { provider: "pg", schema }),
  user: {
    additionalFields: {
      nativeLanguage: { type: "string", required: false, defaultValue: "en", input: true },
    },
  },
  emailAndPassword: {
    enabled: true,
    sendResetPassword: async ({ user, url }) => { /* unchanged — existing Resend callback */ },
    revokeSessionsOnPasswordReset: true,
  },
  session: {
    cookieCache: { enabled: true, maxAge: 300 }, // unchanged (27-01/D-03)
  },
  trustedOrigins: [
    "leocards://",
    ...(process.env.NODE_ENV === "development"
      ? ["exp://", "exp://**", "exp://192.168.*.*:*/**"]
      : []),
  ],
  // expo() MUST come before nextCookies() — nextCookies() must stay last (existing constraint)
  plugins: [expo(), nextCookies()],
});
```

### Pattern 4: Offline screen with NetInfo auto-recover

**What:** D-32's manual-retry + auto-dismiss offline screen.
**When to use:** A top-level wrapper or route-level check, `mobile/components/offline-screen.tsx`.
**Example:**

```tsx
import NetInfo from "@react-native-community/netinfo";
import { useEffect, useState } from "react";

export function useIsOnline() {
  const [isOnline, setIsOnline] = useState(true);
  useEffect(() => {
    return NetInfo.addEventListener((state) => {
      setIsOnline(state.isInternetReachable ?? state.isConnected ?? false);
    });
  }, []);
  return isOnline;
}
```


### Anti-Patterns to Avoid

- **Hand-rolling cookie/session storage:** Writing a custom SecureStore wrapper that parses `Set-Cookie` headers, tracks expiry, and normalises key names is exactly what `expoClient()`'s `storageAdapter` already does (verified from source) — including the ~2KB chunking workaround. Don't rebuild it.
- **Forcing the peer-dependency mismatch:** Do not `npm install --legacy-peer-deps` or `--force` to install `@better-auth/expo` against the current `better-auth@1.5.6` — this silently ships an unsupported combination on the app's most security-sensitive surface. Bump `better-auth` first, deliberately, as its own reviewed step.
- **Reaching for `expo-web-browser` for D-21's password-reset link:** The web reset page should open in the phone's system browser (per D-21's own wording), which is React Native's core `Linking.openURL()` — not `expo-web-browser`'s in-app browser modal (that package is only needed for OAuth flows, which LeoCards v1 doesn't have).
- **Assuming `trustedOrigins`'s dev-mode auto-`exp://` covers everything:** The `expo()` plugin only auto-adds `"exp://"` when `NODE_ENV==="development"` server-side — it does not add the app's own `leocards://` scheme. Both must be present for the D-36 prod-proof run (which is not `NODE_ENV=development`).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Secure session/cookie storage on native (chunking large values, colon-unsafe key names, cookie-expiry parsing) | A custom SecureStore wrapper + manual `Set-Cookie` parser | `@better-auth/expo/client`'s `expoClient()` + internal `storageAdapter` | Verified from source: already chunks values >1800 chars across `<key>.0..N` with a fail-closed marker, normalises colons to underscores (works around a real, documented Keychain limitation), and tracks per-cookie expiry |
| Native origin/CORS trust for a custom-scheme app | Manual header injection + an allow-list check in every route handler | `expo()` server plugin's `onRequest` hook + `trustedOrigins` | One declarative array vs. hand-rolled middleware; matches the pattern the official plugin already ships |
| Auth-gated navigation state machine | Scattered `useEffect` + `router.replace()` redirect checks across every screen | expo-router's `<Stack.Protected guard={...}>` | Declarative, centralised in the root layout, matches the current official pattern |
| Reachability polling for the offline screen | `setInterval` + `fetch("/ping")` | `@react-native-community/netinfo`'s `addEventListener` | Native OS-level connectivity APIs with configurable reachability semantics; no polling overhead or battery cost |
| Custom font asset pipeline for Baloo 2 / Figtree | Manually downloading, licensing-tracking, and bundling `.ttf` files | `@expo-google-fonts/baloo-2` + `@expo-google-fonts/figtree` | Pre-packaged, MIT-licensed, maintained under the official `expo` GitHub org, exact weight subsets importable by name |

**Key insight:** Every "don't hand-roll" item above already exists as official, source-verified, Expo-Go-compatible tooling — this phase's job is wiring existing pieces together (server plugin + client plugin + SecureStore + NetInfo + expo-router), not building new primitives.

## Common Pitfalls

### Pitfall 1: The peer-dependency floor is a hard mechanical requirement, not a discretionary security nicety
**What goes wrong:** Someone runs `npm install @better-auth/expo` against the current lockfile and either hits an ERESOLVE error, or force-installs past it and ships an unsupported version combination.
**Why it happens:** `@better-auth/expo@1.6.26`'s `peerDependencies` require `better-auth: ^1.6.26` exactly `[VERIFIED: npm view @better-auth/expo peerDependencies]`; the repo has `better-auth@1.5.6` installed.
**How to avoid:** Treat the version bump as its own reviewed, isolated wave — bump `better-auth` (and let its own dependency tree pull `@better-auth/core`, `@better-auth/drizzle-adapter`, etc. to matching 1.6.26 versions), run the FULL existing regression suite (`tsc`, `vitest run`, `npm run build`, `qa:run`), get Josh's push approval, deploy, *then* add `@better-auth/expo`.
**Warning signs:** Any ERESOLVE warning during `npm install`; any `--force`/`--legacy-peer-deps` flag appearing in a plan or commit.

### Pitfall 2: `nextCookies()` plugin ordering still applies
**What goes wrong:** Adding `expo()` after `nextCookies()` in the `plugins` array.
**Why it happens:** `nextCookies()` needs to be the last plugin (existing, pre-established constraint per CONTEXT.md and the current `auth.ts` comment).
**How to avoid:** `plugins: [expo(), nextCookies()]` — expo first.
**Warning signs:** Cookies not being set correctly on native sign-in/sign-up responses.

### Pitfall 3: "Optional" peer dependencies are not optional at runtime for this app
**What goes wrong:** Skipping `expo-linking`/`expo-constants` because `@better-auth/expo`'s `peerDependenciesMeta` marks them `optional: true` and the docs page frames them as "optional for social providers."
**Why it happens:** The *compiled* `dist/client.js` unconditionally does `import Constants from "expo-constants"; import * as Linking from "expo-linking";` at module top level `[VERIFIED: downloaded tarball source]` — used for the scheme-fallback and the `expo-origin` header on every non-idToken request, i.e. the plain email/password flow LeoCards uses. `peerDependenciesMeta: optional` only means npm won't hard-fail the *install*; it says nothing about whether the code path is reachable.
**How to avoid:** Install both regardless of "optional" framing (they're needed anyway via expo-router's own install list, so this is close to a non-issue in practice — just don't skip them if scoping expo-router out for any reason).
**Warning signs:** Metro bundler error "Unable to resolve module expo-constants" (or `expo-linking`) the moment `expoClient()` is imported.

### Pitfall 4: The official Expo integration doc is version-stale relative to the installed SDK
**What goes wrong:** Trusting every detail of `better-auth.com/docs/integrations/expo` at face value.
**Why it happens:** The page states it "targets Expo SDK 55" `[CITED: better-auth.com/docs/integrations/expo]`; the installed scaffold is SDK 57. The core plugin API was independently verified unaffected by reading the actual compiled source — but this was only possible because the package was downloaded ad hoc this session (`npm pack`); it isn't installed in the project yet.
**How to avoid:** Once `@better-auth/expo` actually lands in `mobile/node_modules`, re-check its own `README.md`/`dist/*.d.ts` in place per AGENTS.md's installed-docs mandate — don't just trust this research's snapshot forever.
**Warning signs:** Any behaviour that doesn't match the Code Examples above once real code is running.

### Pitfall 5: Expo Go forbids native config plugins — fonts must load at runtime
**What goes wrong:** Reaching for a config-plugin-based custom-font setup (common in bare/prebuild RN projects).
**Why it happens:** D-34 locks the whole phase to Expo Go, which is a fixed pre-built binary — it cannot pick up native config changes without a full dev-client rebuild.
**How to avoid:** Use the runtime `useFonts()` hook (Pattern 5) exclusively.
**Warning signs:** Fonts render as the system default in Expo Go despite "correct" config in `app.json`.

### Pitfall 6: CSS techniques in the web Daybreak components don't translate 1:1 to RN
**What goes wrong:** Trying to copy `auth-card.tsx`'s inline `style={{ background: "linear-gradient(...)" }}` or `boxShadow: "..."` directly into a React Native `style` prop.
**Why it happens:** RN's `StyleSheet`/style objects don't support CSS gradient syntax or `boxShadow` strings — need `expo-linear-gradient`'s `<LinearGradient>` component and platform-specific `shadowColor`/`shadowOffset`/`shadowOpacity`/`shadowRadius` (iOS) + `elevation` (Android) props instead.
**How to avoid:** Budget explicit translation time per component; `auth-card.tsx` and `lion-face.tsx` are otherwise good candidates since both are pure inline-style objects with no Tailwind classes to untangle.
**Warning signs:** Gradients/shadows silently no-op (RN ignores unrecognised style keys rather than erroring).

### Pitfall 7: `npm install` vs `npx expo install`
**What goes wrong:** Plain `npm install <package>` inside `mobile/` can resolve a version outside the SDK 57 compatibility window.
**Why it happens:** `npx expo install` consults the SDK's own compatibility table (the same `bundledNativeModules.json` this research read directly) and pins the matching range automatically; plain npm just takes whatever `^`/`latest` resolves to on the public registry.
**How to avoid:** Always use `npx expo install <package>` for any Expo-ecosystem package inside `mobile/`.
**Warning signs:** A version in `mobile/package.json` that doesn't match the `~57.0.x` pattern seen in `bundledNativeModules.json`.

### Pitfall 8: `trustedOrigins` needs the literal app scheme, not just the Expo Go dev wildcard
**What goes wrong:** Assuming the `exp://` dev-mode auto-trust (added by `expo()`'s `init()` only when `NODE_ENV==="development"`) is sufficient.
**Why it happens:** The client sends `"expo-origin": Linking.createURL("", { scheme: "leocards" })` (≈ `"leocards:///"`) once `expoClient({ scheme: "leocards" })` is configured — verified from source — and the server's `onRequest` hook copies that value into the standard `origin` header for the trust check. The auto-added `"exp://"` entry doesn't match that.
**How to avoid:** Explicitly include `"leocards://"` in `trustedOrigins` (see Pattern 1) — required for both local dev testing *and* the D-36 prod-proof run, which isn't running with `NODE_ENV=development` on Vercel.
**Warning signs:** Native requests failing with an origin/CSRF-style rejection despite `NODE_ENV=development` locally.

### Pitfall 9: Android tooling not confirmed present on this development machine
**What goes wrong:** Planning assumes the Android emulator (D-33's second done-bar leg) is ready to go.
**Why it happens:** This research session's shell had no `adb`, no `emulator`, and empty `ANDROID_HOME`/`ANDROID_SDK_ROOT` `[VERIFIED: direct shell probe]` — this may simply reflect a PATH difference in how this particular tool session was spawned rather than genuine absence of Android Studio on Josh's machine.
**How to avoid:** Confirm directly with Josh (or a fresh terminal check) before the plan relies on the Android leg of D-33 being a zero-setup step.
**Warning signs:** `npx expo start` failing to detect/launch an Android emulator.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | yes | better-auth `emailAndPassword` (server, unchanged) + `@better-auth/expo` official client integration (native) — no hand-rolled credential handling |
| V3 Session Management | yes | `session.cookieCache` (unchanged) + `expoClient`'s SecureStore-backed session storage (native Keychain/Keystore) + the `getSession`/`getSessionFresh`-equivalent split (NAT-03) for revocation-sensitive reads |
| V4 Access Control | partial | 28.2 has no roles/permissions surface — access is purely "has a valid session or not," enforced server-side per-endpoint (pre-existing, unaffected by this phase) |
| V5 Input Validation | yes | zod (or `zod/mini`, see Open Question #1) schemas for native signup/login/forgot-password forms, mirroring the web's existing validated field rules |
| V6 Cryptography | yes — never hand-rolled | Session tokens stored via `expo-secure-store`, which delegates to the OS-native iOS Keychain / Android Keystore; password hashing remains entirely server-side inside better-auth (pre-existing, unaffected) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Origin spoofing via the native `expo-origin` header | Spoofing | Server-side `trustedOrigins` allow-list (Pattern 1) — only listed origins are trusted regardless of what a client claims |
| Account takeover via pre-account hijacking (GHSA-qq9h-g4jm-xgf3 class) | Spoofing/Elevation of Privilege | Confirmed not applicable to LeoCards' current plugin configuration (no magic-link/email-OTP) `[CITED: GitHub Security Advisories]` — re-verify this stays true if any future plugin using passwordless verification is ever added |
| Open redirect via the password-reset `redirectTo` parameter | Tampering | Hardcode/constant the web reset-page URL server-side or validate it against an allow-list — do not accept an arbitrary client-supplied redirect target (the web app already guards an analogous `callbackUrl` pattern in `login/page.tsx` — mirror that same-origin-only discipline) |
| Stale/revoked session still accepted on a device | Elevation of Privilege | The `getSession`/`getSessionFresh`-equivalent split (Pattern 2) — any future revocation-sensitive native call site must use the fresh variant, exactly as the web's `/account` mutations already do |
| Sensitive value overflow silently dropped from secure storage | Information Disclosure / Data Loss | Already handled by `expoClient`'s internal chunking (verified from source) — don't add a second, competing chunking layer on top |
