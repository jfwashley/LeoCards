<objective>
Close the auth loop: gate the two route groups on the session, land a revoked session on login with
the friendly D-24 note, and put sign-out behind the header account glyph.

Purpose: everything before this plan builds pieces; this is where they become an app. NAT-03's
sign-out clause lives here, D-24's "never an unexplained bounce" promise gets its mechanism, and
D-27's header glyph is deliberately the exact seam Phase 28.5 grows into the real account section —
nothing should need moving later.

The revocation check is also where NAT-03's session semantics become observable rather than theoretical:
at boot, a restored session is validated with the cache-bypassing fresh read, so a session revoked on
the web (a password change or reset) is caught on the next launch instead of lingering for up to five
minutes of cookie cache.

Output: the root guard, the boot revocation check, the header, the account sheet, and a tested rule
distinguishing "you were signed out" from "you signed out".
</objective>

<planner_decisions>
- **One declarative guard in the root layout, not per-screen redirect checks.** RESEARCH's "Don't
  Hand-Roll" table names scattered `useEffect` + `router.replace` checks as the anti-pattern precisely
  because one missing check opens the whole shell. expo-router's `Stack.Protected` puts the decision in
  a single place. Verify the exact API against the INSTALLED expo-router docs before writing it —
  AGENTS.md's installed-docs mandate, and RESEARCH Pitfall 4 already caught one doc page being
  SDK-stale.
- **The D-24 notice fires on revocation, never on a deliberate sign-out.** D-24's wording is about
  never leaving a user confused by an unexplained bounce; a user who just tapped "Sign out" is not
  confused, and telling them "you've been signed out" would read as condescending. The distinguishing
  rule is small enough to be pure, so it gets a unit test rather than a comment.
- **Boot validates a restored session with the fresh read.** A session restored from SecureStore has
  only ever been checked against a cookie cache that can be up to five minutes stale. Calling
  `getSessionFresh()` once, after the client resolves and only when a session was restored, is what
  makes NAT-03's "revocation-sensitive paths use fresh session reads" true in practice rather than just
  available as a helper. One extra request per cold launch is a fair price.
- **No mid-session 401 interceptor is built this phase.** 28.2 makes no non-auth API calls, so there is
  nothing to intercept. RESEARCH Open Question 5 asked whether to build the seam now: `session-gate.ts`
  plus `session-notice.ts` ARE that seam, so 28.3 wires its fetch failures into an existing rule
  instead of retrofitting one. Building a fetch wrapper with no caller would be speculative.
- **`app/index.tsx` becomes the session-aware entry rather than being deleted.** expo-router needs an
  index route; making it the place that waits for the session and hands off to the guard keeps the
  routing decision in one obvious file for whoever reads this codebase next.
- **The account glyph opens a sheet; it does not navigate.** D-27 is explicit that this same entry point
  becomes the real account section in 28.5 — "nothing moves, it grows". The web glyph navigates to
  `/account`; native must not, because that route does not exist yet and inventing one would be exactly
  the thing that has to move later.
</planner_decisions>

**Session guard (RESEARCH Pattern 3, from the current official expo-router docs).** The root layout
reads session state from `authClient.useSession()`, renders nothing while it is pending (the splash
stays up, held by plan 28.2-05's font gate), and then renders a `Stack` where the `(tabs)` group is
guarded on having a session and the `(auth)` group on not having one.

**Boot revocation check (D-24).** Once the session resolves and only when a session was restored, call
`getSessionFresh()` from `mobile/lib/auth-client.ts` exactly once per cold launch. If it returns no
session, the stored session is dead: sign out locally, raise the D-24 notice, and let the guard route
to login. If it returns a session, do nothing further. Never run this check on every render or on every
navigation — once per launch, guarded by a ref or equivalent.

**Notice rule (`mobile/lib/session-gate.ts`).** A tiny pure module with one decision: given whether a
session existed before, whether one exists now, and whether the disappearance was deliberate, decide
whether to raise the D-24 notice. Deliberate sign-out never notifies; an involuntary disappearance
always does; and the deliberate flag is one-shot, so a later involuntary loss still notifies. It marks
sign-outs as deliberate for the account sheet to call before `signOut()`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored session → authorisation decision | A token restored from SecureStore decides whether the tab shell renders; it has only ever been validated against a cache that can be five minutes stale |
| server-side revocation → device | A password change or reset on the web revokes sessions server-side; the device must notice |
| user intent → notice copy | The app must distinguish a deliberate sign-out from an involuntary one to avoid both silent bounces and condescending messages |

|-----------|----------|-----------|-------------|-----------------|
| T-28.2-38 | Elevation of Privilege | Restored session at cold launch | mitigate | The boot check calls `getSessionFresh()` (cache-bypassing) whenever a session is restored, so a session revoked on the web is caught at the next launch rather than lingering for the cookie cache's five-minute TTL. This is the concrete realisation of NAT-03's "revocation-sensitive paths use fresh session reads" |
| T-28.2-39 | Elevation of Privilege | Route gating | mitigate | One declarative guard in the root layout, with an acceptance-criteria scan asserting no per-screen login redirect exists under `(tabs)`. Scattered checks are the failure mode RESEARCH's "Don't Hand-Roll" table names: a single missing check opens the entire shell |
| T-28.2-40 | Spoofing | Unexplained bounce to login | mitigate | D-24's notice, raised by a unit-tested rule, so a revoked session presents as an explained app state rather than a bare credential prompt — the ambiguity a phishing lookalike depends on |
