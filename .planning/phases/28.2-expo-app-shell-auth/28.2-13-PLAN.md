Deliver NAT-04: the app is online-required, and wherever the network is missing it shows a friendly
Leo-branded screen with a retry that also recovers on its own.

— the screen dismisses itself when the device reports connectivity is back, and the button stays for
impatient taps. The subtlety worth engineering is the middle state: Android in particular reports

connection is fine is worse than showing nothing.

mount covering both the auth screens and the tab shell.

<planner_decisions>
- **The transition rules are a pure module; the hook is a thin wrapper.** RESEARCH's Validation
  Architecture is explicit that the repo's node-environment vitest cannot exercise the real NetInfo
  native module, and that standing up `jest-expo` for this phase is not worth it. Extracting the rules
  means NAT-04's actual logic is unit-tested against synthetic NetInfo-shaped events, and only the
  subscription itself is left to the manual device check.
- **Unknown reachability preserves the previous state instead of defaulting to offline.** RESEARCH's
  illustrative snippet collapses `isInternetReachable ?? isConnected ?? false`, which reports offline
  whenever the OS has not finished determining reachability — a spurious full-screen interruption for a
  user whose connection is fine. Preserving the previous state costs nothing and removes the flicker.
  An explicit `isConnected: false` still means offline immediately.
- **The screen mounts once at the root, above the navigator.** 28.2-UI-SPEC.md §10.8 leaves placement
  to the planner. One overlay covering both route groups means every screen this phase and every screen
  28.3/28.4 add are covered automatically, with no per-screen wiring to forget.
- **A network failure must never be read as a revoked session.** Plan 28.2-12's boot check calls
  `getSessionFresh()`; if the device is offline that call fails. Failing to distinguish "the server
  said there is no session" from "I could not reach the server" would sign users out every time they
  launched the app on a train. This plan hardens that path as its own acceptance criterion.
- **The app starts optimistic.** Initial state is online, so a cold launch never flashes the offline
  screen before the first NetInfo event arrives.
</planner_decisions>

Auto-recover means the screen simply unmounts the moment the state flips back to online; D-32 requires
no exit transition, and an optional quick fade is fine but not mandatory.

**Connectivity rules (`mobile/components/offline-state.ts`).** A pure reducer over synthetic
NetInfo-shaped events, with no import of `@react-native-community/netinfo` itself, so the node test
environment can load it. RESEARCH names this shape in its Open Question 5 and
28.2-PATTERNS.md Group F carries it forward. Rules:
- explicit `isInternetReachable: true` → online
- explicit `isInternetReachable: false` → offline
- `isInternetReachable` null or undefined with `isConnected: true` → previous state preserved
- `isConnected: false` → offline, regardless of reachability
- a manual retry sets a checking flag; the next event clears it and applies the rules above

**Hook (`mobile/lib/use-is-online.ts`).** Subscribes with `NetInfo.addEventListener`, which fires
immediately with the current state and then on every change, and routes every event through the pure
reducer. It returns the current state plus a retry function that runs `NetInfo.fetch()` and feeds that
result through the same rules. Unsubscribe on unmount — the listener returns its own unsubscribe
function.

`@react-native-community/netinfo` is the D-32 screen's source of truth (installed in plan 28.2-04); it
is deliberately separate from `expo-network`, which exists only so `@better-auth/expo`'s internal
online-manager has an accurate signal.

**Boot-check hardening (interaction with plan 28.2-12).** The root layout's boot revocation check calls
`getSessionFresh()`. Distinguish two outcomes: a resolved response saying there is no session means the
session was revoked (sign out, raise the D-24 notice), while a thrown or network-level failure means
nothing about the session and must leave it untouched. When offline, skip or defer the check entirely
rather than letting it fail.

**Test template:** `packages/domain/src/study/study-engine.test.ts` — plain describe/it/expect, no
mocking, synthetic fixture objects. Mobile tests import relatively; the root vitest config aliases `@`
to the WEB app's `./src`.
</interfaces>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS connectivity signal → app state | A device-level signal decides whether the app blocks its entire UI |
| network failure → session state | A failed request must not be interpreted as an authorisation decision |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28.2-43 | Denial of Service (own-goal) | Boot revocation check while offline | mitigate | The check is skipped when offline, and a thrown/network failure is explicitly distinguished from a resolved no-session response. Without this split, a user launching the app with no signal would be signed out of a perfectly valid session — a self-inflicted denial of service on every commute |
| T-28.2-44 | Denial of Service (own-goal) | Spurious offline overlay | mitigate | Unknown reachability preserves the previous state rather than defaulting to offline, and the overlay is suppressed while the splash is held. A full-screen block triggered by a transient OS reading is a self-inflicted outage |
| T-28.2-45 | Information Disclosure | Offline screen copy | mitigate | The screen states only that the connection is missing — no endpoint, no host, no error detail. RESEARCH's own "no blank screens, no raw errors" framing for NAT-04 |
| T-28.2-46 | Denial of Service (battery/network) | Connectivity detection | mitigate | Event-driven `NetInfo.addEventListener` only, asserted by a grep forbidding `setInterval`. Polling would drain battery for a strictly worse signal |
