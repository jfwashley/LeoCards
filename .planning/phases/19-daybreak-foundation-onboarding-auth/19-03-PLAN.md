<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client form → better-auth API | Email (forgot) and new password + reset token (reset) cross from the untrusted client into better-auth's `requestPasswordReset`/`resetPassword` handlers. |
| email link → reset page | The reset token arrives via a URL query param the user clicks from email — untrusted, possibly expired/tampered. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-03-ENUM | Information Disclosure (account enumeration) | Forgot confirmation copy | mitigate | Confirmation reads "If an account exists, we've sent a reset link…" and is shown identically whether or not the email is registered; the e2e spec asserts this exact phrasing. Replaces the prior existence-implying copy. |
| T-19-03-TOKEN | Tampering / Spoofing | Reset token from URL | mitigate | Preserve better-auth `resetPassword({ newPassword, token })` — token validity is enforced server-side by better-auth; the UI never trusts the token, and an invalid/expired token routes to the safe dead-end. `revokeSessionsOnPasswordReset: true` (auth.ts) is unchanged. |
| T-19-03-MATCH | Tampering (weak input) | Reset password fields | mitigate | Keep the zod `.refine` password-match + min-8 client check; better-auth re-validates server-side. |
| T-19-03-LEAK | Information Disclosure | Reset error copy | mitigate | The expired/invalid path shows a generic "This reset link has expired" message — it does not distinguish "wrong token" from "expired token" from "already used", avoiding oracle leakage. |
</threat_model>
