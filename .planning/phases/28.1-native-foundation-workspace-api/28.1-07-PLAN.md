<objective>
Complete NAT-02's endpoint surface with the three remaining native-v1 operations: creating a card
(manual add-a-word), creating a deck (so a freshly signed-up native user can get started), and
reading account basics.

Purpose: with `GET /api/dashboard` and `GET /api/study` already landed, these three close the
native-v1 read/write set. `POST /api/cards` and `POST /api/decks` are pure adapters over the core
functions plan 28.1-04 extracted — they add no business logic, which is the whole point of D-03.
`GET /api/account` is the one revocation-sensitive endpoint in this phase and must use the
cookie-cache-bypassing session read, mirroring the `/account` page's existing precedent.

Output: three route handlers with tests, one small account core, and a delegating `/account` page.
</objective>

<planner_decisions>
- **DR-04 — `POST /api/decks` is in scope.** RESEARCH Open Question 1 asked whether deck creation
  belongs to this phase. It does: D-10's native v1 includes sign-up, and a user who has just
  signed up owns no deck. The web resolves that via `/welcome`, whose first step calls the
  `createDeck` server action — a web-only path. Without this endpoint, native v1 is structurally
  broken for every new user, which contradicts NAT-02's "every read/write the native v1 needs".
  28.3 still owns the native onboarding *screen*; this plan owns the endpoint it calls.

- **What is deliberately NOT built (and why it is not a gap):**
  - **Sign up / sign in / sign out / change password.** Already REST-reachable through
    better-auth's existing `/api/auth/[...all]` catch-all — `change-password-card.tsx` already
    calls `authClient.changePassword(...)` through it today. RESEARCH Pitfall 8 is explicit that
    adding `/api/account/change-password` would be redundant. Native attaches the Expo auth client
    in 28.2; no new server surface is needed.
  - **`/api/habitat`.** Already exists and already returns exactly the `HabitatState` shape the
    habitat screen composes. RESEARCH names re-doing it as an anti-pattern.
  - **`/api/translate`, `/api/extract`, `/api/cards/[id]/pause`, `/api/cards/[id]/unpause`,
    `/api/study/complete`.** All already client-consumable and unchanged.
  - **Card edit/delete, wordlist add/remove, image-card batch save.** Not in D-10's native-v1 bar;
    image-to-flashcards and Browse Words parity are explicit programme-level deferrals.

- **Auth per endpoint.** `POST /api/cards` and `POST /api/decks` use the cached fast path
  (raw `auth.api.getSession({ headers: await headers() })`), matching all six existing handlers.
  `GET /api/account` uses the fresh read (`query: { disableCookieCache: true }`) because it is the
  revocation-sensitive surface — this mirrors `getSessionFresh()`'s internals
  (`src/lib/auth-session.ts` lines 30-34) and the `/account` page's Phase 27-01 precedent
  (D-03/D-04). The route handler must NOT import `getSessionFresh()` itself: that wrapper is
  `react`'s `cache()`, meant for RSC render-pass dedup only.

- **Rate limits.** `POST /api/cards` 30/min (mirrors `pause`'s cheap-single-row-write budget and
  supports rapid manual entry). `POST /api/decks` 10/min (deck creation is rare; a tight ceiling
  caps deck-spam). `GET /api/account` 30/min (each call is a live DB session read by design, so
  it is the most expensive read in the set).
</planner_decisions>
