<planner_decisions>
- **DR-03 (RESEARCH Open Question 4) — ONE error convention, locked here before any endpoint
  exists.** Extracted core functions return
  `CoreResult<T> = { ok: true; data: T } | { ok: false; code: CoreErrorCode }` where
  `CoreErrorCode = "unauthorized" | "forbidden" | "invalid" | "rate-limited"`.
  `CORE_ERROR_STATUS` maps them to 401 / 403 / 400 / 429. Each entry point adapts:
  a **route handler** returns `Response.json({ error: code }, { status: CORE_ERROR_STATUS[code] })`;
  a **server action** throws `new Error("Unauthorized" | "Forbidden" | ...)` preserving its
  existing caller contract byte-for-byte. This generalises `requestEmailChange`'s already-shipped
  discriminated-union shape (`src/lib/account-actions.ts` lines 58-64), which 28.1-PATTERNS.md
  identifies as the stronger of the two conventions currently coexisting in this repo.
  There is deliberately **no `not-found` code**: T-12-08 requires 403 on a missing-or-foreign
  resource, never 404, so a not-found concept would invite an existence leak.

- **DR-08 — the shared schemas use FULL `zod`, not `zod/mini`.** The two schemas being relocated
  (`GradeSchema`, `CommitSchema`) currently run in production on the app's hottest write path.
  Rewriting them into zod/mini's `.check(...)` dialect during a relocation would put a subtle
  validation-semantics regression on the SRS commit endpoint for zero functional gain in this
  phase. Verbatim relocation is the zero-risk move. The web's PERF-14 win is protected instead by
  DR-02's export map (`./schemas` is never re-exported from `.`, `./study` or `./habitat`) plus
  the automated firewall test added in Task 3. Web client components keep importing `zod/mini`
  locally, exactly as today; nothing in this plan changes any client component. If a native
  screen in 28.3 wants a lighter validator, that is a 28.3 decision with its own measurement —
  not a 28.1 rewrite of a live endpoint.

- **`packages/domain` gains exactly one dependency: `zod`, at the root's existing `^4.3.6`
  range.** This deliberately supersedes 28.1-01's "no dependencies" state. That criterion was
  a Wave-1 checkpoint, not a permanent rule — the permanent rule is DR-02's firewall, which is
  now enforced by the Task 3 test rather than by a zero-deps assertion. No NEW package enters
  the dependency tree (zod is already a root dependency, `[VERIFIED: package.json]`), so no
  package-legitimacy checkpoint applies.
</planner_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted HTTP request body → `/api/study/complete` | The SRS commit endpoint's zod validation is the only thing standing between a forged body and `recall_events` / card mastery writes |
| shared package → web client bundle | `./schemas` carries zod at runtime; the root and engine subpaths must not |
