## Phase Boundary

Phase 28.1 is the FOUNDATION sub-phase of the native rewrite programme (28.1-28.5). It delivers NAT-01 and NAT-02:

- **NAT-01 (workspace):** The repo becomes a workspaces monorepo — `mobile/` (Expo) + `packages/` (shared TS) alongside the **unchanged root Next.js app** — with shared domain packages holding the SRS rules, habitat-state maths, zod schemas, and API contract types, **imported by the web app** (D-06/D-07).
- **NAT-02 (API):** Every read/write the native v1 needs is exposed as a screen-shaped REST `/api/*` route handler (one request per screen load) validated by the shared zod schemas; web server actions delegate to the same core functions; **`qa:run` and `perf:recert` stay green throughout the conversion** (D-03/D-04).

**NOT this sub-phase:** Expo app functionality (28.2 boots the shell + auth; 28.1 only establishes the `mobile/` workspace member), native core-loop screens (28.3), native habitat (28.4), builds/identity/delivery (28.5). No database schema changes, no new user-facing features, no web UI changes — web behaviour unchanged throughout.

**Depends on:** Phase 18's PERF-06 re-cert gate (shipped 18-05) as the regression guard for backend changes; 18-06 (field-comparison doc) may close in parallel — no hard block.

## Implementation Decisions

Carried verbatim from 28-CONTEXT.md `<decisions>`; original D-IDs preserved. Decisions owned by later sub-phases (D-08/D-09/D-11/D-13/D-14/D-16/D-17/D-18/D-19/D-20) are deliberately absent — see the parent file.

### Architecture (trackable in 28.1 plans)
- **D-03: Backend = the existing Next.js/Vercel deployment, unchanged role.** Server-action mutations convert to real `/api/*` route handlers the RN app calls; better-auth stays (Expo client plugin); Neon/Drizzle/DeepL/Claude untouched. The web app keeps working unchanged throughout the conversion (server actions delegate to the same extracted core functions).
- **D-04: API style = REST route handlers, screen-shaped.** One request per screen load (the PERF-16 consolidation philosophy carried forward), extending the existing `/api/*` conventions; shared zod schemas validate both ends. Perf analysis accepted: REST ≈ tRPC > GraphQL at this scale — round-trip count and payload shape are what matter, not transport style.
- **D-06: Repo layout = same repo, workspaces.** Add `mobile/` (Expo) + `packages/` (shared TS) alongside the root Next.js app. No `apps/web` restructure of the just-certified web app; one git history, one `.planning/`.
- **D-07: Shared domain package(s).** SRS rules, habitat-state maths, zod schemas, and API request/response contract types extracted into `packages/` and imported by BOTH apps — study behaviour and validation identical on web and native by construction. (In 28.1 the consuming apps are the web app + the API contract surface; the Expo app starts importing them from 28.2.)
- **D-02: Stack = React Native + Expo.** The `mobile/` workspace member exists for the Expo app; full EAS/boot bring-up is 28.2's job — 28.1 establishes the workspace home so the monorepo shape is proven.
- **D-10: v1 feature bar = core loop + basic account.** This defines the native-v1 endpoint surface NAT-02 must cover: sign up/in/out (better-auth handler already exists), dashboard, study sessions, manual add-a-word, habitat; basic account (view details, sign out) lands by 28.5.

### Programme framing [informational]
- **D-01 [informational]: Native rewrite.** Capacitor shell, PWA+TWA, and the split approach were all explicitly declined; Josh chose the rewrite knowingly. Phase 28 became this multi-sub-phase programme.
- **D-05 [informational]: Web app stays first-class permanently.** Hence "web behaviour unchanged throughout" is a hard bar for this sub-phase, not a nice-to-have.
- **D-15 [informational]: Online-required v1.** SRS state stays server-authoritative and conflict-free — no offline/sync affordances belong in the API design.

### Claude's Discretion
- Shared-package boundaries and build wiring (workspaces config, TS project refs).
- API endpoint naming, error shape, and pagination details (within D-04's screen-shaped rule).
- Degree of `mobile/` scaffolding in this sub-phase (minimal Expo scaffold vs bare workspace stub) — 28.2 owns boot, navigation shell, and auth.

## Existing Code Insights

Carried from 28-CONTEXT.md (scouted 2026-07-30: no PWA/manifest/service-worker/native groundwork exists anywhere — greenfield on the mobile side).

### Reusable Assets
- **Pure-TS domain modules ripe for `packages/` extraction (D-07):** SRS round/direction/cooldown rules, `computeHabitatState` + decay maths, zod schemas, image/validation constants — all framework-free today
- **Already-client-consumable API routes:** `/api/study/complete`, `/api/translate`, `/api/extract`, `/api/habitat`, better-auth handler — the conversion pattern the remaining server actions follow
- e2e `*test.local` user convention + `scripts/cleanup-test-users.mjs` — reuse for API integration tests

### Established Patterns
- **Screen-shaped payloads** (PERF-15/16) — the REST endpoint design rule (D-04)
- **Batched writes** (26-02 `db.batch()`, 26-03 multi-row insert) — API handlers must reuse the same core functions, not re-implement
- **Session caching semantics** (27-01): cached `getSession()` vs `getSessionFresh()` for revocation-sensitive paths — the API layer must preserve the split
- **Pushes are releases** (27 D-11): every push to main auto-deploys prod — during API-ification the live web app is affected by every backend change; Josh approves every push

### Integration Points
- `src/lib/auth.ts` — better-auth server config (trustedOrigins for the future native origin)
- Server actions (`src/lib/deck-actions.ts` etc.) — extract shared core functions; actions and new route handlers both delegate to them
- Root `package.json` — workspaces conversion (D-06)
- Phase 18 `perf:recert` + Phase 15 `qa:run` — the safety nets that gate every backend-touching wave

## Specific Ideas

- Josh probed API-style performance directly; locked REST after the analysis that transport is a wash at this scale — **"round trips per screen and payload shape are what matter"** should govern endpoint design.
- Every push to main auto-deploys prod: sequence the conversion so the web app is never broken between waves — server actions delegating to extracted core functions is the mechanism that keeps each push safe.

</specifics>
