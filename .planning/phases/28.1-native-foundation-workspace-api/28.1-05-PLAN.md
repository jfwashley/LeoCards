<objective>
Extract the dashboard screen's composition — decks, the active deck's cards, the assembled study
session, the derived due/cooldown/paused/sleeping flags and the habitat state — into one core
function, expose it as `GET /api/dashboard`, and make the existing RSC page delegate to it.

Purpose: the dashboard is the single largest read in native v1 and the one RESEARCH flags most
sharply (Pitfall 9): its flags are derived inline in the Server Component today, so an endpoint
that only re-exposed raw rows would force the native client to reimplement "what counts as due" —
breaking D-07's "identical by construction" guarantee. One core function, two entry points, is
the only shape that satisfies both D-03 and D-07.

Output: `src/lib/core/dashboard.ts`, `GET /api/dashboard` with tests, and a delegating RSC page.
</objective>

<planner_decisions>
- **DR-04 (RESEARCH Open Question 1) — the zero-deck case ships as an explicit
  `needsOnboarding: true` signal with `decks: []`, and `POST /api/decks` IS in scope for this
  phase (plan 28.1-07).** NAT-02 requires "every read/write the native v1 needs". D-10's native
  v1 includes sign-up; a user who has just signed up has no deck, and the web flow resolves that
  by redirecting to `/welcome`, whose first step calls the `createDeck` server action. Without a
  deck-creation endpoint, native v1 is structurally broken for every new user — so it is a
  native-v1 write, not an onboarding-screen concern deferred to 28.3. 28.3 still owns the native
  onboarding *screen*; 28.1 owns the endpoint it will call.

- **DR-07 — endpoint naming and response envelope.** `GET /api/dashboard`. Success returns the
  raw `DashboardResponse` object with NO envelope wrapper; errors return `{ error: "..." }` plus
  an HTTP status. This is the universal convention across all six existing route handlers
  (`{ success: true, leveledUp }`, `{ pausedAt }`, `{ translation }`, the bare `HabitatState`) —
  never `{ data: {...} }`.

- **Auth: cached fast path.** `/api/dashboard` is a read-mostly screen load, so it uses the same
  raw `auth.api.getSession({ headers: await headers() })` call every existing route handler uses,
  relying on better-auth's own 5-minute `session.cookieCache`. The `disableCookieCache` fresh-read
  variant is reserved for the revocation-sensitive `/api/account` endpoint (plan 28.1-07),
  mirroring the `/account` page precedent from Phase 27-01.

- **Rate limit: 60 requests/minute/user.** Generous for real navigation (the web dashboard is the
  app's hub and users bounce back to it constantly) but a hard ceiling on the polling pattern
  RESEARCH names as this phase's live DoS threat. Declared at module scope with
  `createRateLimiter`, exactly like the four existing limiters.

- **Test split.** `src/lib/core/dashboard.test.ts` owns the DB-shaped behaviour (query counts,
  derived flags, masking). `src/app/api/dashboard/route.test.ts` mocks the core module and owns
  only the HTTP concerns (401 / 429 / status mapping / body shape). This keeps the route test
  small and avoids re-mocking a five-query composition through chained Drizzle builders.
</planner_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated HTTP → `GET /api/dashboard` | New public route surface; the session check is the only gate |
| caller-supplied `?deck=` → returned card data | An attacker-chosen deck id reaches a data-selection path |
| screen-shaped payload → client | One response now carries decks, cards, habitat and derived state together |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28.1-20 | Elevation of Privilege | `?deck=` deck selection | mitigate | The active deck is resolved by `decks.find(...)` over the result of `getUserDecks(session.user.id)`, so a forged or foreign id can only fall back to the caller's own first deck — it can never select another user's deck.
