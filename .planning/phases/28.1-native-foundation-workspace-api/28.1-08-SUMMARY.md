## Decisions Made

- **React/react-dom version:** pinned to `19.2.3` rather than the root app's `19.2.4`. Verified empirically (not assumed) via two independent live sources: `npm view react-native@0.86.2 peerDependencies` returns `react: "^19.2.3"`, and `expo@57.0.10`'s own `bundledNativeModules.json` (fetched live from the registry CDN) pins `react`/`react-dom` to exactly `19.2.3` as its recommended companion versions. npm correctly nested `mobile/node_modules/react@19.2.3` alongside the unchanged root `node_modules/react@19.2.4` — exactly the scenario 28.1-01's unanchored `.gitignore` `node_modules` pattern was added to cover.
- **`mobile/index.ts` uses `React.createElement`, not JSX.** JSX syntax is only valid in `.tsx` (or `.jsx`) files — the TypeScript grammar parses `<Foo>` inside a plain `.ts` file as an old-style type-assertion cast, not JSX, which would fail to parse for a `<View>...</View>` shape. The plan names the literal filename `mobile/index.ts` in five separate places (frontmatter `files_modified`, the `must_haves.artifacts` path, the `key_links` pattern, the action text, and the acceptance criteria), so renaming to `.tsx` would contradict the plan's explicit intent. `createElement(View, null, createElement(Text, null, label))` is semantically identical to the JSX form (JSX compiles down to exactly this) and keeps the file valid, literal-filename-compliant TypeScript. Both `habitatLevel` and `LEVEL_THRESHOLDS` are genuinely used in the computed `label` that flows into the rendered `Text`, so this is not a vacuous import.
- **`expo export --no-bytecode` used for the literal-search evidence.** See Deviations below for the full reasoning — Expo SDK 57 defaults Android exports to compiled Hermes bytecode, which isn't grep-able.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Hermes bytecode default blocked the plan's literal-search verification step**
- **Found during:** Task 3, step 4 (searching the exported bundle for the `LEVEL_THRESHOLDS` literal sequence)
- **Issue:** The plan's literally-instructed run, `npx expo export --platform android --output-dir dist`, exited 0 and bundled 578 modules (genuine proof of successful Metro resolution) — but Expo SDK 57's Android export defaults to compiled Hermes bytecode (`.hbc`, confirmed via `file`: "Hermes JavaScript bytecode, version 98"), a binary format. A direct binary grep for the literal sequence `5,15,30,50,80,120,170,230` returned 0 matches, since Hermes bytecode stores numeric constants in a binary constant pool, not as searchable ASCII text.
- **Fix:** Re-ran the identical `--platform android` export with the documented `--no-bytecode` CLI flag (`npx expo export --help` lists it: "Prevent generating Hermes bytecode"). This keeps the exact platform originally instructed and the exact same Metro resolver — it only changes the output serialization format. The resulting 916 KB plain-JS bundle contains the exact sequence intact: `u=[5,15,30,50,80,120,170,230],l=60` (the minified `LEVEL_THRESHOLDS` immediately followed by the minified `EXCITED_WINDOW_MINUTES`), which is strong, non-coincidental evidence that `habitat-engine.ts`'s real runtime code — not just its type — was bundled.
- **Files modified:** none (verification-only; no `watchFolders`/`nodeModulesPaths` or any other manual monorepo wiring was added — `mobile/metro.config.js` was re-checked and confirmed unchanged after both export runs, satisfying the plan's explicit prohibition on papering over resolution issues with manual config)
- **Verification:** `mobile/metro.config.js` still contains no `watchFolders`/`nodeModulesPaths`; both export runs exited 0; `mobile/dist/` deleted after use; `git status --porcelain` clean of export artefacts
