# Phase 28.1: Code Review Report

**Reviewed:** 2026-08-04T21:02:45Z
**Depth:** standard
**Files Reviewed:** 80

## Summary

Reviewed the npm-workspaces conversion (@leocards/domain), the extracted transport-agnostic cores under `src/lib/core/`, the five native-v1 REST endpoints, the mobile Expo workspace member, and the import-path-rewritten components. Review effort was weighted toward the new code per phase guidance; every changed file was read in full, and behaviour of the extractions was verified against the pre-phase source (`git show f63c57e^:...`) where equivalence was claimed.

The security posture of the new surface is solid: all five endpoints authenticate, ownership gates use combined-WHERE queries with the deliberate 403-never-404 convention, request bodies are schema-validated with over-posting protection, user IDs are only ever taken from the session, and all SQL is parameterised through drizzle. The engine relocation is faithful (verified verbatim R099 renames) and the extracted cores reproduce the pre-extraction page logic exactly, including the paused-card masking and qaMode gating. No hardcoded secrets, no debug artifacts, no injection vectors found.

No Critical findings. Seven Warnings concern real robustness/consistency defects that will bite as the native client (28.2+) starts consuming this surface: an inconsistent error-body vocabulary across the REST surface, a rate-limiting model whose per-instance in-memory state cannot deliver the "hard ceiling" the route comments claim on Vercel serverless, a rate-limit gate ordered after the expensive operation it exists to meter, a contract type whose documentation omits its masking semantics, legacy write paths that bypass the new 500-char validation invariant, a pre-existing dead-end error loop on quit-with-zero-grades, and an unguarded infinite loop in an exported shared-package function. As the phase is already deployed, all findings are triaged as follow-up fixes.

## Warnings

### WR-01: "Save and quit" with zero grades sends a guaranteed-invalid commit and traps the user in a dead-end retry loop

**File:** `src/components/study-session.tsx:135-138, 262-306` (interacts with `packages/domain/src/schemas/study.ts:16`)
**Issue:** `QUIT_SESSION` unconditionally transitions to `{ phase: "committing", graded: state.graded }` with no emptiness guard. If the user opens a session and taps "Save and quit" before grading any card, the commit effect POSTs `grades: []` to `/api/study/complete`. `CommitSchema` requires `grades: z.array(GradeSchema).min(1)`, so the server always returns 400, the client throws on `!response.ok`, and the user lands on the error screen whose only affordance is "Retry saving session" — which re-POSTs the same empty batch and fails forever. The quit dialog's copy ("Your progress so far will be saved") is also false in this case. Pre-existing behaviour (schema relocated verbatim this phase), but the file is in scope and the dead end is user-reachable on the first card of every session.
**Fix:**
```tsx
case "QUIT_SESSION": {
  if (state.phase !== "studying") return state;
  if (state.graded.length === 0) {
    // Nothing to save — skip the commit entirely.
    return { phase: "end", stats: { cardsStudied: 0, correctCount: 0, newlyLearned: 0, leveledUp: null } };
  }
  return { phase: "committing", graded: state.graded };
}
```
(or navigate straight back to `/dashboard?deck=${deckId}` when `graded.length === 0`).

### WR-02: In-memory rate limiter cannot enforce the documented ceilings on the Vercel serverless deployment

**File:** `src/app/api/dashboard/route.ts:14-20`, `src/app/api/study/route.ts:10-17`, `src/app/api/cards/route.ts:9-15`, `src/app/api/decks/route.ts:9-15`, `src/app/api/account/route.ts:22-27` (mechanism: `src/lib/rate-limit.ts`)
**Issue:** All five new endpoints describe their limiter as "a hard ceiling on the polling pattern RESEARCH names as this phase's live DoS threat". `createRateLimiter` is a module-scoped in-memory `Map`; its own header says "Suitable for single-server deployment. For horizontal scaling, replace with Redis-backed implementation." This repo deploys to Vercel (git-connected auto-deploy per AGENTS.md), where each serverless/fluid instance holds an isolated map that also resets on every cold start. An attacker (or a buggy native polling loop — precisely the named threat) that fans out across N concurrent instances gets N x 60 req/min, and any instance recycle resets the window. The mitigation is real but materially weaker than the comments assert, and this phase multiplied the endpoints relying on it. Pre-existing pattern, newly extended.
**Fix:** Either back the limiter with a shared store (Upstash Redis / Vercel KV — the swap point is already isolated in `createRateLimiter`), or correct the five route comments to state the per-instance/best-effort semantics so future phases don't build on a false invariant.

### WR-03: /api/account performs the expensive cache-bypassing session read BEFORE the rate-limit check that exists to meter it

**File:** `src/app/api/account/route.ts:29-51`
**Issue:** The route comment justifies the 30/min ceiling because "each call is a live session read by design (the cache bypass above), making this the most expensive read in the native-v1 set; the ceiling reflects that cost". But the order is: (1) `auth.api.getSession({ ..., query: { disableCookieCache: true } })` — the expensive fresh DB read — then (2) `accountLimiter.check(session.user.id)`. A rate-limited caller still triggers the full fresh session read on every request; the 429 only protects `loadAccountCore` (one cheap `verification` select). The limiter therefore does not meter the cost it was sized for. Keying by user id forces auth-first ordering, so the current design cannot deliver its stated goal.
**Fix:** Key this limiter on a pre-auth identifier (e.g. hash of the session cookie value, falling back to IP) and check it before the fresh session read; or accept and document that the ceiling protects only the post-auth composition, not the session read.

### WR-04: Error-body vocabulary is inconsistent across the native-facing REST surface (lowercase codes vs capitalised strings)

**File:** `src/app/api/cards/route.ts:62,67,78-81`; `src/app/api/decks/route.ts:59,64,74-79`; `src/app/api/study/route.ts:73-78`; `src/app/api/study/complete/route.ts:105,110,149,158`; `src/app/api/cards/[id]/unpause/route.ts:73`
**Issue:** The new adapters return machine codes from the DR-03 contract for core failures — `{ error: "forbidden" }`, `{ error: "invalid" }` — while (a) their own route-level 400s return `{ error: "Invalid input" }`, and (b) the pre-existing endpoints the native client will equally depend on (`/api/study/complete`, `/api/cards/[id]/pause`, `/api/cards/[id]/unpause`) return `{ error: "Forbidden" }`, `{ error: "Invalid input" }`, `{ error: "Invalid card" }`. Concretely: a 400 from `GET /api/study` says `"invalid"` but a 400 from `POST /api/cards` says `"Invalid input"`; a 403 from `POST /api/cards` says `"forbidden"` but a 403 from `POST /api/cards/[id]/unpause` says `"Forbidden"`. Any native client that branches on the error string (the only machine-readable discriminator the surface offers beside status) must special-case per endpoint, and the contract's stated convention (`Response.json({ error: code }, ...)` in `contracts/errors.ts`) is only true for the five new routes.
**Fix:** Normalise every native-reachable endpoint on the lowercase `CoreErrorCode` strings (map the legacy handlers' literals through `CORE_ERROR_STATUS`'s keys), and change the new routes' body-parse/schema-fail 400s from `"Invalid input"` to `"invalid"` so one endpoint never speaks two dialects. Document the body shape in `contracts/errors.ts`.

### WR-05: DashboardResponse contract silently omits the qaMode masking semantics of `cards[].cooldownUntil` and `cards[].masteryRound`

**File:** `packages/domain/src/contracts/dashboard.ts:23-31` (behaviour: `src/lib/core/dashboard.ts:132-146`)
**Issue:** The contract declares `cooldownUntil: string | null` and `masteryRound: number` with no qualifier, and its doc block explains other fields at length. In reality `loadDashboardCore` returns `cooldownUntil: null` for every card unless the caller holds a valid QA cookie (`qaMode`), and masks `masteryRound` to `0` for paused cards regardless of stored value. The masking is deliberate (per phase context), but it is documented only inside `src/lib/core/dashboard.ts` — which a native integrator consuming the contracts package will never read. A 28.2 native developer will reasonably build per-card cooldown UI against this type and receive permanent nulls in production.
**Fix:** Add to the `DashboardResponse` doc block (and inline on the two fields): "`cooldownUntil` is always null unless the caller is QA-authenticated; per-card cooldown state is intentionally not exposed to customers — use the top-level `earliestCooldownEnd`. Paused cards always read `masteryRound: 0`."

### WR-06: Legacy write paths bypass the 500-char/non-empty card-text invariant the new schema enforces

**File:** `src/lib/deck-actions.ts:80-101` (`editCard`), `src/lib/deck-actions.ts:138-166` (`addWordToCard`)
**Issue:** This phase routed `saveCard` through `CreateCardSchema` (`min(1).max(500)` on both faces, T-28.1-12), and `saveImageCards` already enforces the same bounds. But `editCard` writes client-supplied `front`/`back` to the DB with no validation at all — no emptiness check, no length bound — so any user can create a card via the validated path and then edit it to an arbitrarily large payload (unbounded row growth, and unbounded text fed to every renderer of card faces), or blank both faces. `addWordToCard` likewise inserts client-supplied `front`/`back` with no bounds. The 500-char invariant the schema tests pin ("cannot silently loosen") is therefore not an invariant: it is trivially bypassed one server action away.
**Fix:** Validate in both actions with the shared schema before writing, e.g.:
```ts
const parsed = CreateCardSchema.pick({ front: true, back: true }).safeParse({ front, back });
if (!parsed.success) throw new Error("Invalid card data");
```
(or route `addWordToCard` through `saveCardCore`, which is the D-03 mechanism this phase built for exactly this purpose).

### WR-07: `interleave()` in the shared domain package infinite-loops for `interval <= 0`

**File:** `packages/domain/src/study/study-engine.ts:112-142`
**Issue:** `interleave` is an exported member of `@leocards/domain/study` — public API for web today and native from 28.3. For `interval = 0` (or any value < 1) with non-empty `learning` and `resurface`, once `resurface` is exhausted while `li < learning.length`, each loop iteration computes `chunkEnd = Math.min(li + 0, learning.length) = li`, the inner while never advances `li`, the resurface branch no longer pushes, and the outer `while (li < learning.length || ...)` never terminates — hanging the server request or the native JS thread. Current callers always pass `3`, so this is latent, but a shared package must not export a function whose plausible-looking argument hangs the process.
**Fix:**
```ts
export function interleave(learning: CardForSession[], resurface: CardForSession[], interval: number): CardForSession[] {
  const step = Math.max(1, Math.floor(interval)); // guard: interval < 1 would never advance li
  // ...use `step` in place of `interval` below
}
```

## Info

### IN-01: `loadDashboardCore` and `loadAccountCore` can never fail, leaving unreachable error branches in their adapters

**File:** `src/lib/core/dashboard.ts:42-181`, `src/lib/core/account.ts:17-44`; dead branches at `src/app/api/dashboard/route.ts:87-92`, `src/app/api/account/route.ts:64-69`, `src/app/(protected)/dashboard/page.tsx:217`, `src/app/(protected)/account/page.tsx:41`
**Issue:** Both cores only ever return `{ ok: true, ... }` (every code path), so the `if (!result.ok)` mappings in their two routes and two pages are unreachable, and the route tests exercising "returns 403 when the core reports forbidden" test a state the real core cannot produce. Harmless (uniform adapter shape is a reasonable choice), but worth knowing the branches are dead so nobody relies on them for error handling.
**Fix:** Either accept as deliberate uniformity (add a one-line comment "core currently cannot fail; branch kept for CoreResult uniformity"), or narrow the return types to `CoreResult` only where failure is possible.

### IN-02: `LANGUAGE_LABELS` exists in four copies despite the "one map, one source of truth" claim

**File:** `src/lib/core/decks.ts:34-38` (claims single source), duplicates at `src/app/(protected)/dashboard/page.tsx:16-20`, `src/app/(protected)/account/page.tsx:12-16`, `src/components/deck-view.tsx:20-24`
**Issue:** The core exports `LANGUAGE_LABELS` with a comment that deck-actions "imports this rather than keeping a second copy — one map, one source of truth", yet three presentation-layer copies remain (one added to the account page this phase). Adding a language now requires 4+ coordinated edits plus `CreateDeckSchema`'s enum; a missed copy degrades silently to the raw code (`?? language` fallback).
**Fix:** Import the map (type-only-safe, dependency-free) from `@/lib/core/decks` — or move it into `@leocards/domain` alongside the language enum so web and native share it.

### IN-03: `src/lib/habitat-ui-utils.ts` is a dead module kept alive only by its own test

**File:** `src/lib/habitat-ui-utils.ts:1-129`
**Issue:** Repo-wide, the only importer of `getMoodTransitionType` / `getLayersForLevel` / `getDecayAlpha` / `getTigerPosition` / `getTigerFacing` is `src/lib/__tests__/habitat-ui-utils.test.ts`. The module also contains an unreachable `level >= 10` branch (engine caps at 9). It received an import rewrite this phase, so it will keep compiling forever while shipping nothing.
**Fix:** Delete the module and its test (git history preserves it), or annotate why it is retained (e.g. planned native reuse).

### IN-04: habitat-engine doc drift — "level 10" comments for a level-9-capped engine, plus an always-true guard

**File:** `packages/domain/src/habitat/habitat-engine.ts:98, 260-263`
**Issue:** `HabitatState.nextLevelThreshold` is documented as "null when already at level 10", and `computeHabitatState` guards `if (level < 10)` — but `habitatLevel` and the override clamp both cap level at 9, so the guard is always true and the doc names a level that cannot exist. Now that this file is the shared-contract source for native, doc accuracy matters more.
**Fix:** Change the doc to "null when already at level 9 (max)" and drop the `level < 10` guard (or replace with `LEVEL_THRESHOLDS[level - 1] ?? null` unconditionally, which already yields null at 9).

### IN-05: Dashboard clamps `?celebrate` into [1,10] while the habitat page allow-lists [1,9]

**File:** `src/app/(protected)/dashboard/page.tsx:198-202` vs `src/app/(protected)/habitat/page.tsx:23-30`
**Issue:** Dashboard converts `?celebrate=999` to `10` (a level that does not exist, and which the habitat page it links to will then reject to null), while habitat rejects out-of-range values outright. Cosmetic inconsistency in sibling guards for the same parameter; pre-existing, carried through the rewrite.
**Fix:** Mirror the habitat page's reject-to-null validation with the [1,9] bound.

### IN-06: GET /api/habitat has no rate limiter while every sibling native-v1 read does

**File:** `src/app/api/habitat/route.ts:24-48`
**Issue:** The new reads (`/api/dashboard`, `/api/study`, `/api/account`) all carry per-user limiters justified by the polling DoS threat; `/api/habitat` — an equally pollable authenticated read that hits `getHabitatFacts` (two queries) and is fetched client-side by `habitat-scene.tsx`'s retry — has none. If the polling threat justifies limiters on the new reads, it applies here identically.
**Fix:** Add the same `createRateLimiter({ windowMs: 60_000, maxRequests: 60 })` gate after auth.

### IN-07: Bundle-firewall and workspace smoke tests have blind spots that weaken their guarantees

**File:** `src/lib/__tests__/domain-bundle-firewall.test.ts:50-72`, `packages/domain/src/__tests__/smoke.test.ts:24-29`
**Issue:** (a) The firewall's client check matches only the double-quoted `"use client"` literal and only DIRECT imports of `@leocards/domain/schemas` — a single-quoted directive or a client component importing a non-"use client" helper that itself imports the schemas subpath both slip through (the second is the realistic regression path for the PERF-14 win it guards). (b) The smoke test's namespace assertion (`expect(typeof domain).toBe("object")`) is vacuous: the root barrel re-exports only types, so the namespace is an empty object and the assertion passes even if runtime resolution of the workspace symlink half-works; only the type-level `CardId` import does real work.
**Fix:** (a) match `['"]use client['"]` and consider asserting on the built client bundle (or at least also scanning files transitively imported by "use client" files); (b) import a runtime value by package subpath (e.g. `LEVEL_THRESHOLDS` from `@leocards/domain/habitat`) and assert its contents.

### IN-08: `createDeckCore` deck-name numbering has a read-then-insert race producing duplicate names

**File:** `src/lib/core/decks.ts:60-72`
**Issue:** `n = count(existing) + 1` followed by a separate insert means two concurrent creates for the same user+language both compute the same `n` and persist two decks named e.g. "French #2". No uniqueness constraint exists on `(userId, name)`. Display-only consequence; logic relocated verbatim this phase, and the new rate limit (10/min) narrows but does not close the window (POST /api/decks now makes concurrent programmatic creation easy).
**Fix:** Accept (cosmetic), or derive the name from a `count(*)` in the same statement / add a retry on a `(userId, name)` unique index if distinct names ever matter.

### IN-09: `addWordToCard` / `removeWordFromDeck` use the two-step ownership check instead of the combined-WHERE gate

**File:** `src/lib/deck-actions.ts:148-154, 298-304`
**Issue:** Both fetch the deck by id alone (`where(eq(decks.id, deckId))`) and compare `deck.userId !== userId` in application code, while `saveCardCore`, `saveImageCards`, `loadStudySessionCore` and `getSameLanguageDeckBackWords` all use the single combined-WHERE gate (IN-01 pattern) the core comments call the mechanism that "structurally cannot return a foreign-user deck row". Functionally equivalent outcomes (both resolve to Forbidden), but the codebase now documents one canonical pattern and ships two.
**Fix:** Convert both to `where(and(eq(decks.id, ...), eq(decks.userId, userId)))`, or route `addWordToCard` through `saveCardCore` (which also closes its WR-06 validation gap).

### IN-10: mood-decay lerp comment contradicts the code

**File:** `src/lib/habitat-3d/mood-decay.ts:136-140`
**Issue:** Comment says "use 0.08 per call for snappy convergence" while the code lerps with `* 0.25`. Dev-capture-only module (excluded from production bundles), import-path-only change this phase, but the drift will mislead the next tuning pass.
**Fix:** Update the comment to the actual 0.25 factor (or vice versa).
