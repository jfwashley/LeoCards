- **DR-01 (RESEARCH Open Question 2) — ONE package.** `packages/domain`, npm name
  `@leocards/domain`. No `packages/schemas` split. ~900 lines of pure logic does not justify
  two packages; splitting later is a cheap npm-workspaces move.

- **DR-02 — Subpath export map, NOT a single collapsed barrel.** The package exposes six entry
  points: `.` (ids only), `./ids`, `./study`, `./habitat`, `./schemas`, `./contracts`.
  Web code imports `@leocards/domain/study` and `@leocards/domain/habitat` as 1:1 replacements
  for today's `@/lib/study-engine` and `@/lib/habitat-engine`. Two hard reasons this is not
  negotiable:
  1. **Test isolation.** `src/app/api/study/__tests__/cooldown-config.test.ts` calls
     `vi.mock("@/lib/habitat-engine", ...)` AND `vi.mock("@/lib/study-engine", async (importOriginal) => ...)`
     in the same file (lines 30 and 38). Collapsing both engines behind one module id would make
     the two mocks collide and silently break that test — and the same double-mock shape appears
     in `src/app/api/study/complete/route.test.ts` and `src/app/api/debug/__tests__/state.test.ts`.
     Distinct subpaths keep every existing `vi.mock` a pure string swap.
  2. **Bundle firewall.** Zod schemas live behind `./schemas` and are NEVER re-exported from
     `.`, `./study` or `./habitat`. 24 web files (many `"use client"`) import habitat-engine
     types; a barrel that pulled zod transitively would risk undoing PERF-14's shipped
     client-bundle reduction.

- **DR-09 — `src/db/schema.ts` RE-EXPORTS, it does not merely import.** 25 files across the repo
  do `import type { UserId } from "@/db/schema"`. A plain `import type` in schema.ts would stop
  re-exporting them and break all 25. Use `export type { ... } from "@leocards/domain";` so all
  25 consumers stay byte-unchanged. (28.1-PATTERNS.md Group F shows an `import type` line — that
  is the one place its excerpt is incomplete; follow this decision, not that excerpt.)

- **DR-05 (28.1-PATTERNS.md scope flag) — `wordlist.ts`, `image-constants.ts`,
  `image-validation.ts` are NOT relocated in phase 28.1.** D-07 names exactly four things for
  the shared package: SRS rules, habitat-state maths, zod schemas, API contract types. These
  three are none of them; no NAT-02 endpoint consumes them; `wordlist.ts` would drag 7 more
  files (`src/data/wordlists/*`) across the boundary; and the modes they back (wordlist-browse,
  image-extract) are programme-level deferrals in 28-CONTEXT.md. Excluding them honours D-07
  exactly rather than reducing it.

- **No `"type"` field in `packages/domain/package.json`.** The root `package.json` also omits it
  and contains ESM `.ts`; every consumer here (Turbopack, Vite/Vitest, Metro, drizzle-kit's
  esbuild loader) reads the TS module syntax directly. Fallback if any tool errors on module
  format: add `"type": "module"` and re-run the same gates.
</planner_decisions>
