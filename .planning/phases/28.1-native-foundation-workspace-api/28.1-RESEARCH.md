# Phase 28.1: Native foundation — workspace & API - Research

**Researched:** 2026-08-03
**Domain:** npm workspaces monorepo conversion (Next.js 16 app at repo root + Expo/RN sibling) and Next.js Route Handler extraction from Server Actions
**Confidence:** MEDIUM-HIGH (repo-internal findings are HIGH — verified by direct file reads; Expo/RN ecosystem findings are MEDIUM — officially sourced but fast-moving, see Assumptions Log)

## Summary

This phase converts LeoCards' root `package.json` into an npm workspaces root (`mobile/` + `packages/*` as new members, the Next.js app staying unmoved at the repo root per D-06) and extracts a handful of framework-free domain modules plus a new REST endpoint surface so a future native client can consume the same backend the web app already uses. The repo-side investigation (direct file reads of `package.json`, `tsconfig.json`, `biome.json`, `.gitignore`, `vitest.config.ts`, every existing `/api/*` route handler, both server-action files, and five candidate domain modules) surfaced a clean, low-risk starting position: the domain logic (`study-engine.ts`, `habitat-engine.ts`, `wordlist.ts`, `image-constants.ts`, `image-validation.ts`) is genuinely framework-free today, the existing route handlers already share one consistent auth/rate-limit/validate/ownership/error convention worth extending, and Next.js 16's App Router auto-bundles workspace packages inside Server Components and Route Handlers with no build step required. Three concrete traps were found by reading the actual config files rather than assuming: the root `tsconfig.json`'s `**/*.ts` include glob will greedily pull `mobile/`'s React-Native-only TypeScript into the web app's typecheck unless excluded; `.gitignore`'s `/node_modules` entry is root-anchored and will not cover `mobile/node_modules/`; and the branded ID types (`UserId`, `CardId`, etc.) that the domain modules `import type` today live inside `src/db/schema.ts`, which is the wrong direction for a shared package to depend on — they need to move into the new package instead.

On the Expo/React-Native side, live registry verification (`npm view expo dist-tags`, run during this research) found `expo@57.0.9` as current latest — two full SDK generations ahead of the SDK 54/55 figures returned by web search and even by better-auth's own live-fetched integration docs, which is a concrete, evidenced demonstration of why this research treats every specific SDK/RN version number as provisional and re-verifiable rather than locked. better-auth's Expo support ships as a **separate** package (`@better-auth/expo`, not a subpath of the installed `better-auth@1.5.6`), which 28.2 — not this phase — will add; 28.1 only needs to avoid creating a workspace shape that package can't later live in, which Expo's own first-class, zero-config monorepo support (auto-configured Metro since SDK 52+) satisfies without any special wiring in this phase.

**Primary recommendation:** Add `"workspaces": ["mobile", "packages/*"]` to the existing root `package.json` (no other root fields change), create one shared package (`packages/domain`, scope `@leocards/`) holding the relocated domain logic + branded ID types + zod/mini schemas, extend the existing route-handler conventions (session check via raw `auth.api.getSession`, per-user rate limiting, zod `.safeParse`, DB-join ownership checks returning 403) to the new screen-shaped endpoints, and reconcile the two currently-divergent server-action error conventions into one extracted-core-function pattern before the first new endpoint is built.

### Pattern 1: Existing Route Handler Convention (extend, don't reinvent)
**What:** Every existing `/api/*` route handler (`study/complete`, `translate`, `extract`, `cards/[id]/pause`) follows the identical sequence: raw session check → per-user rate limit → JSON parse in try/catch → zod `.safeParse` → DB-join ownership check (403, never 404) → business logic → `Response.json(...)`.
**When to use:** Every new screen-shaped endpoint this phase adds.
**Example (condensed from `src/app/api/cards/[id]/pause/route.ts`, read directly from this repo):**
```typescript
// Source: src/app/api/cards/[id]/pause/route.ts (this repo, verified)
export async function POST(_req: NextRequest, ctx: { params: Promise<{ id: string }> }) {
  const session = await auth.api.getSession({ headers: await headers() }); // raw call — NOT the RSC-only cached wrapper, see Pitfall 7
  if (!session) return Response.json({ error: "Unauthorized" }, { status: 401 });

  const limit = someLimiter.check(session.user.id);
  if (!limit.allowed) {
    return Response.json({ error: "Too many requests" }, {
      status: 429,
      headers: { "Retry-After": String(Math.ceil(limit.retryAfterMs / 1000)) },
    });
  }

  const [owned] = await db.select(/* ... */).from(cards).innerJoin(decks, /* ... */)
    .where(and(eq(cards.id, id), eq(decks.userId, session.user.id)));
  if (!owned) return Response.json({ error: "Forbidden" }, { status: 403 }); // never 404 — T-12-08

  // ... business logic ...
  return Response.json({ /* raw data, no envelope wrapper */ });
}
```
**Note on session check:** every existing route handler calls `auth.api.getSession` **directly**, not the React-`cache()`-wrapped `getSession()`/`getSessionFresh()` from `src/lib/auth-session.ts` — those wrappers exist for RSC page dedup only. New route handlers should follow the existing route-handler convention (raw call, relies on better-auth's own `session.cookieCache` 5-min TTL for the fast path), reserving `getSessionFresh()`'s `disableCookieCache` semantics only for genuinely revocation-sensitive new endpoints (mirroring the `/account` precedent).

### Pattern 2: Workspace Package Consumption — No Build Step
**What:** Next.js 16's App Router automatically bundles packages imported inside Server Components and Route Handlers — `[CITED: node_modules/next/dist/docs/01-app/02-guides/package-bundling.md]`. The doc's explicit "opt out" mechanism (`serverExternalPackages`) only makes sense if bundling is already the default for these two surfaces; no `transpilePackages` entry is documented as required for that path specifically.
**When to use:** Importing `packages/domain` from any Route Handler or Server Component (RSC pages, the new API routes).
**Recommended defensive addition:** the docs' `transpilePackages` page and the Pages-Router-scoped section of the same guide describe it as the general-purpose "transpile a monorepo package" mechanism, and it is explicitly still current (no deprecation notice, `v13.0.0` addition). The guide's wording does **not** explicitly confirm the same zero-config bundling extends to a **Client Component** (`"use client"`) importing a workspace package — this repo has several (e.g. a future client-side add-a-word form importing a shared zod schema). Add `transpilePackages` defensively — it is a no-op cost when unnecessary and closes this one ambiguity:
```typescript
// Source: node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/transpilePackages.md (this repo, verified)
const nextConfig: NextConfig = {
  transpilePackages: ["@leocards/domain"],
  // ...existing headers() block, unchanged
};
```
**Package shape (no build step):** `packages/domain/package.json`'s `main`/`types` fields point directly at TypeScript source (e.g. `"main": "./src/index.ts"`). Both Next's bundler (Turbopack, default in this repo's installed Next 16.2.1) and Expo's Metro (via Babel) can transpile TS-from-node_modules-symlink directly — no `tsup`/`tsc --watch` pipeline needed, avoiding the classic monorepo "forgot to rebuild the shared package" bug class.

### Pattern 3: Metro Monorepo Auto-Configuration (Expo side)
**What:** Expo has had first-class, **zero-manual-config** monorepo support since SDK 52+ — `[CITED: docs.expo.dev/guides/monorepos]`. If a prior manual `watchFolders`/`nodeModulesPaths` config exists it must be deleted (not applicable here — greenfield).
**Example:**
```javascript
// Source: docs.expo.dev/guides/monorepos (fetched this session)
// mobile/metro.config.js
const { getDefaultConfig } = require('expo/metro-config');
const config = getDefaultConfig(__dirname);
module.exports = config;
```
No `watchFolders` entry pointing at `../packages/domain` is required — Expo's Metro config auto-detects the npm-workspaces root and resolves siblings through the standard node_modules symlink.

### Anti-Patterns to Avoid
- **Two independent copies of validation/business logic (one per entry point):** the whole point of D-03/D-07 is that server actions and route handlers call the *same* extracted function. Writing a second, route-handler-flavored copy of `computeCardUpdate` or the ownership check defeats the phase's purpose and creates exactly the drift D-07 exists to prevent.
- **Treating `/api/habitat` as needing work:** it already returns exactly the `HabitatState` shape `habitat/page.tsx` composes — see Pitfall 15. Spend the wave budget on `dashboard`/`study`/`new-card`/`account`, which have no existing endpoint at all.
- **Assuming Vercel's monorepo docs about `apps/web` subfolders apply here:** D-06 keeps the Next app at the repo root — this is the *simpler* Vercel monorepo case (Root Directory stays unset), not the harder one those tutorials solve for. See Pitfall 10.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Rate limiting new endpoints | A new limiter implementation | `createRateLimiter` from `@/lib/rate-limit.ts` | Already proven across 4 existing routes; consistent `Retry-After` behavior |
| Session/auth checking | Manual cookie/token parsing | `auth.api.getSession({ headers: await headers() })` (route handlers) / `getSession()`/`getSessionFresh()` (RSC only) | Security-critical, already correctly split on revocation semantics (27-01/D-04) |
| Ownership verification | A generic ACL/permissions layer | The established single-query JOIN chain (card→deck→user), returning 403 never 404 | Matches the documented T-12-08 convention; a new pattern would be inconsistent with every existing endpoint |
| Request/response validation | Hand-written runtime type guards | zod (`.safeParse()`), shared via `packages/domain/src/schemas` | D-04 mandates this explicitly; it's this codebase's universal convention already |
| Metro monorepo wiring | Manual `watchFolders`/`nodeModulesPaths` | `expo/metro-config`'s `getDefaultConfig()` | Official, zero-maintenance, avoids the classic pre-SDK-52 RN-monorepo pain this project would otherwise hit |
| Shared-package build pipeline | `tsup`/`rollup --watch` producing `dist/` | Ship TS source directly via `main`/`types` in `package.json`; let Next/Turbopack and Metro/Babel transpile on demand | Avoids stale-dist bugs (the #1 monorepo footgun); zero extra tooling to maintain |
| Cross-entry-point error handling | A second bespoke error-shape per new route handler | One extracted core function returning a typed result; each entry point (action vs. route) adapts it to its own existing caller contract | This *is* the D-03 mechanism itself — the specific adapter shape is discretion, but "one source of truth" is not |

**Key insight:** almost everything this phase needs a *pattern* for already exists once in this codebase — the risk is inventing a second, subtly different version of something that already works, not the absence of a solution.

## Common Pitfalls

### Pitfall 1: Root `tsconfig.json`'s greedy include glob will pull in `mobile/`
**What goes wrong:** `tsc --noEmit` (the project's typecheck gate, run in CI) starts failing once `mobile/` contains real Expo/RN TypeScript, because it references RN-only globals/types the web app's `"lib": ["dom", "dom.iterable", "esnext"]` doesn't provide.
**Why it happens:** The root `tsconfig.json`'s `"include"` is `["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts", ".next/dev/types/**/*.ts", "**/*.mts"]` and `"exclude"` is only `["node_modules"]` `[VERIFIED: repo tsconfig.json]` — a repo-wide glob with no `mobile` carve-out.
**How to avoid:** Add `"mobile"` to the root `exclude` array before (or in the same commit as) scaffolding `mobile/`. Give `mobile/` its own independent tsconfig (Expo's own `create-expo-app` output extends `expo/tsconfig.base` and is fully self-contained). `packages/*` can reasonably stay inside the root project's include glob since the domain logic has no DOM/RN-specific requirements either way.
**Warning signs:** `npx tsc --noEmit` at the repo root suddenly reports errors in files under `mobile/` referencing types like RN's `ViewStyle` or JSX intrinsics the web tsconfig's `jsx: "react-jsx"` + DOM lib don't recognize.

### Pitfall 2: `.gitignore`'s `/node_modules` is root-anchored
**What goes wrong:** A nested `mobile/node_modules/` (npm workspaces still nests packages that have real version conflicts, e.g. Expo's own tightly-pinned React) gets tracked by git, and — because `biome.json` sets `"vcs": {"useIgnoreFile": true}` — Biome also stops excluding it, so `npm run lint` (repo-wide, see Pitfall 3) attempts to scan thousands of vendored files.
**Why it happens:** `.gitignore` line 4 is `/node_modules` — the leading slash anchors the pattern to the repo root only; it does not match `mobile/node_modules` or `packages/*/node_modules` `[VERIFIED: repo .gitignore]`.
**How to avoid:** Change to an unanchored `node_modules` (matches at any depth) or add explicit `mobile/node_modules` / `packages/*/node_modules` entries, before running `npm install` for the first time post-workspaces-conversion.
**Warning signs:** `git status` after the first `npm install` shows thousands of new untracked files under `mobile/node_modules/`.

### Pitfall 3: `npm run lint` is repo-wide; CI's own lint step is not
**What goes wrong:** Confusion about whether adding `mobile/` breaks linting. It breaks the **local** `npm run lint` script but not CI.
**Why it happens:** `package.json`'s `"lint"` script is `"biome ci ."` — repo-wide `[VERIFIED: package.json]`, directly contradicting `AGENTS.md`'s own stated convention ("Scope Biome runs to touched files only — never run it repo-wide"). CI's workflow, however, calls `biome ci src/` directly (not `npm run lint`) `[VERIFIED: .github/workflows/ci.yml]` — already scoped, already safe.
**How to avoid:** Add `mobile/**` (and likely a note about `packages/*` staying in-scope, since it should follow this project's own Biome conventions) to `biome.json`'s `"files.includes"` negation list, e.g. `"includes": ["**", "!**/*.css", "!mobile/**"]`. Expo's default template typically ships its own ESLint config `[ASSUMED]` — recommend leaving `mobile/`'s linting on that toolchain rather than folding RN/Expo JSX conventions into this project's Biome ruleset.
**Warning signs:** A developer runs `npm run lint` locally post-scaffold and gets a wall of errors from generated Expo boilerplate.

### Pitfall 4: `npm ci` fails hard on lockfile drift — sequence the lockfile regeneration
**What goes wrong:** A push that adds `"workspaces"` to `package.json` without a correspondingly-regenerated `package-lock.json` fails CI (`npm ci` in `.github/workflows/ci.yml`) and very likely fails Vercel's own install step too, since every push to `main` auto-deploys prod (AGENTS.md, D-11 from Phase 27).
**Why it happens:** `npm ci` requires the lockfile to exactly match `package.json`; it does not regenerate anything, unlike `npm install` `[VERIFIED: repo .github/workflows/ci.yml uses npm ci]`.
**How to avoid:** Run `npm install` **locally** immediately after adding the `workspaces` field and creating the new member `package.json` files, verify `npm ci` succeeds locally against the regenerated lockfile, and commit the (likely much larger) `package-lock.json` in the same change before pushing.
**Warning signs:** CI or Vercel build logs show `npm ci` exiting non-zero with an "invalid: lock file's ... does not satisfy ..." message.

### Pitfall 5: Branded ID types live in the wrong place for a shared package
**What goes wrong:** `packages/domain`'s relocated `study-engine.ts`/`habitat-engine.ts` currently `import type { CardId, RecallDirection } from "@/db/schema"` / `import type { UserId } from "@/db/schema"` `[VERIFIED: repo study-engine.ts, habitat-engine.ts]` — that `@/` alias is the **root app's own** `tsconfig.json` path mapping (`"@/*": ["./src/*"]`) and will not resolve from inside an independent workspace package.
**Why it happens:** The branded types (`UserId`, `DeckId`, `CardId`, `RecallEventId`, `RecallDirection`) are declared inline in `src/db/schema.ts` alongside the Drizzle table definitions `[VERIFIED: repo db/schema.ts]` — a file that also imports `drizzle-orm/pg-core` at runtime (harmless today only because the domain modules use `import type`, which TypeScript elides).
**How to avoid:** Relocate the branded-type declarations themselves into `packages/domain` (e.g. `packages/domain/src/ids.ts`), then update `src/db/schema.ts` to import them **from** `@leocards/domain` instead of declaring them locally. This reverses the dependency to the conventional direction (shared package is upstream of both consumers) and removes the fragile cross-workspace path-alias dependency entirely.
**Warning signs:** `tsc` inside `packages/domain` reports "Cannot find module '@/db/schema'" once the package has its own independent tsconfig (which it should).

### Pitfall 6: zod/mini lacks `.refine()` as a chainable method
**What goes wrong:** Moving an existing schema like `/api/translate`'s `RequestSchema` (`z.object({...}).refine((v) => ..., {message: ...})`) into `packages/domain` verbatim fails to compile if the package standardizes on `zod/mini`.
**Why it happens:** This is a previously-discovered, already-documented finding from this exact codebase: Phase 27-07 verified live against installed zod 4.3.6 that `zod/mini`'s `z.object()` schemas have **no** `.refine()` method at all `[VERIFIED: .planning/STATE.md Phase 27-07 entry + confirmed pattern reused in change-password-card.tsx, read directly this session]`.
**How to avoid:** Use zod/mini's already-proven-in-this-repo replacement form: `.check(z.refine((data) => ..., { message: ..., path: [...] }))`, exactly as `change-password-card.tsx` and `reset-password/page.tsx` already do.
**Warning signs:** `tsc` reports `Property 'refine' does not exist on type ...` inside a newly-moved schema file.

### Pitfall 7: better-auth's Expo plugin is a separate package, and Expo SDK numbers decay fast
**What goes wrong:** Assuming `@better-auth/expo` ships inside the already-installed `better-auth@1.5.6`, or hardcoding a specific Expo SDK number into a plan/task based on training data or a single web search.
**Why it happens:** The installed `better-auth@1.5.6` package's `exports` map has no `./expo` entry at all `[VERIFIED: node_modules/better-auth/package.json, read directly]` — Expo support is the separate `@better-auth/expo` package. Separately, this research's own web search surfaced "SDK 54/55" while a live registry check the same session found `expo@57.0.9` as current latest (published 2 days prior) `[VERIFIED: npm view expo dist-tags, run this session]` — a concrete, self-demonstrated example of doc/search staleness.
**How to avoid:** 28.2 (not this phase) installs `@better-auth/expo` — verify its peer-dependency range against whatever core `better-auth` version is installed at that time. For 28.1's own Expo scaffold (if any), run `npm view expo dist-tags` immediately before scaffolding rather than trusting any number in this document or in training data.
**Warning signs:** N/A for 28.1 directly — flagging so 28.2 doesn't inherit a stale assumption baked into this phase's plan.

### Pitfall 8: Don't rebuild what better-auth's catch-all route already exposes
**What goes wrong:** Scoping `change-password` (or sign-up/in/out) into NAT-02's "extract a new route handler" list.
**Why it happens:** It's easy to assume every account-related capability needs a bespoke new endpoint. It doesn't — `change-password-card.tsx` already calls `authClient.changePassword(...)` directly `[VERIFIED: repo change-password-card.tsx]`, which better-auth's client SDK routes through the pre-existing `/api/auth/[...all]` catch-all handler. This is already REST-reachable; native just needs the Expo client (28.2), not new server work.
**How to avoid:** Keep NAT-02's actual extraction list to the genuinely-missing endpoints: dashboard load, study session load, add-a-word (card creation + translate is already `/api/translate`), and account-basics view (pendingEmail + display fields — sign-out is also already better-auth's catch-all).
**Warning signs:** A task in the plan proposes a new `/api/account/change-password` route — redundant, don't build it.

### Pitfall 9: Dashboard screen composition is not just queries — it's derived state
**What goes wrong:** Building a new `/api/dashboard`-style endpoint that only re-exposes `getUserDecks`/`getDeckCards` raw rows, forcing the native client to reimplement `hasDueCards`/`dueCount`/`allPaused`/`sleeping`/`earliestCooldownEnd` logic itself — which would violate D-07's "identical by construction" guarantee, since these flags are currently derived inline in the RSC from the very same `study-engine.ts` primitives slated for the shared package.
**Why it happens:** `dashboard/page.tsx` computes this derived state directly in the Server Component body, not in a separate queryable function `[VERIFIED: repo dashboard/page.tsx, read directly — see the `hasDueCards`/`allPaused`/`sleeping` computation block]`.
**How to avoid:** The new dashboard endpoint's core function must replicate this composition (not just the raw queries) using the same relocated `packages/domain` functions (`assembleSession`, `earliestCooldownEnd`), returning the derived flags as explicit JSON fields — exactly mirroring what the RSC does today.
**Warning signs:** The native dashboard screen (28.3) needs its own copy of "what counts as due" logic — a sign this endpoint under-delivered.

### Pitfall 10: Vercel's "apps/web subfolder" monorepo guidance does not apply here
**What goes wrong:** Applying advice found via web search (set Root Directory to the app subfolder, enable "Include files outside Root Directory in the Build Step") to this repo.
**Why it happens:** Most Vercel monorepo tutorials assume the Next app lives in an `apps/web` subfolder with siblings alongside it — a structure D-06 explicitly forbids here. LeoCards' actual layout (Next app at the repo root, `mobile/`+`packages/*` added as new siblings) means the Vercel "Root Directory" setting should stay **unset** (= repo root, unchanged) — the shared `packages/*` are already "inside" the directory Vercel builds from, so the toggle that trips up the `apps/web` pattern doesn't apply `[Reasoned from D-06 + WebSearch of Vercel's documented pattern — MEDIUM confidence, no Vercel doc page found addressing this exact "app stays at root" case explicitly]`.
**How to avoid:** Do not touch Vercel project settings for this phase. Do expect a slower `npm install` step on every deploy once `mobile/`'s dependency tree is present (see below) — that's a real but non-blocking cost of D-06's chosen layout, not a correctness problem.
**Warning signs:** Someone proposes creating a `vercel.json` or changing the Vercel dashboard's Root Directory setting as part of this phase — unnecessary, skip it.

// src/lib/deck-actions.ts's saveCard, reconciling the two existing divergent

async function saveCardCore(input: SaveCardInput): Promise<
  | { ok: true; data: { id: CardId } }
  | { ok: false; code: "unauthorized" | "forbidden" | "invalid" }
> { /* ... */ }

export async function saveCard(deckId: string, front: string, back: string) {
  const result = await saveCardCore({ deckId, front, back });
  if (!result.ok) throw new Error(result.code === "forbidden" ? "Forbidden" : "Unauthorized");
  return result.data;
}

// Route handler adapter (maps to the existing {error} + status convention):
export async function POST(request: Request) {

  if (!result.ok) {

    return Response.json({ error: result.code }, { status });
  }
  return Response.json(result.data);
}

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| IDOR via a new endpoint skipping the ownership JOIN | Tampering / Elevation of Privilege | Reuse the established card→deck→user JOIN chain, 403 on mismatch, never 404 (existence leak) |
| Stale-session replay on a revocation-sensitive new endpoint | Spoofing | Use `getSessionFresh()`'s `disableCookieCache` pattern for anything mutating account/session state; raw cached `auth.api.getSession` is fine for read-mostly screen loads |
| Over-posting / mass assignment via loosely-typed request bodies | Tampering | zod schemas with explicit allow-listed fields only (already this project's universal convention — `GradeSchema`/`CommitSchema` as the template) |
| Resource exhaustion via a native client polling a new endpoint more aggressively than a web page's natural navigation cadence | Denial of Service | Apply `createRateLimiter` to every new endpoint, not just the expensive ones (translate/extract already do this) |
| Response over-fetching / cross-user data leakage in a screen-shaped payload | Information Disclosure | Explicit response shaping per endpoint (PERF-15/16 precedent) — the new dashboard/account endpoints must be audited field-by-field, same discipline as the existing `cardRows`/`dashboard` serialization already applies |
| Native origin not yet trusted by better-auth | Spoofing | Not this phase's concern — `trustedOrigins` gets the Expo scheme added in 28.2; 28.1's new endpoints inherit whatever trust boundary better-auth already enforces (session cookie / bearer, unchanged) |
