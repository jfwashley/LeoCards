<objective>
Extract the two writes that native v1 needs — deck creation and card creation — into core
functions in a new `src/lib/core/` module, and convert the matching server actions into thin
adapters that delegate to them while preserving their existing throw-based caller contract
byte-for-byte.

Purpose: this IS the D-03 mechanism. "Server actions delegate to the same extracted core
functions" is what lets the web app keep working unchanged while its backend becomes an API —
and it is the only thing that prevents the anti-pattern RESEARCH names explicitly (a second,
subtly different copy of the ownership check and business logic living in the route handler).
Plan 28.1-07 builds `POST /api/cards` and `POST /api/decks` on top of these functions.

Output: `src/lib/core/decks.ts`, its unit tests, and two refactored server actions.
</objective>

<planner_decisions>
- **DR-10 — core functions live in `src/lib/core/*.ts`, NOT in `packages/domain`.** They touch
  `db` (Drizzle/Neon) and the app's tables; RESEARCH's Architectural Responsibility Map puts
  every one of these capabilities in the API/Backend tier. `packages/domain` stays pure logic
  with zero infrastructure imports — that purity is what makes it importable from Metro in 28.2.
  `src/lib/core/` is a new directory in this repo; there is no prior convention to match, so
  follow the existing `src/lib/*-queries.ts` file style (module-level doc comment, section
  banners, named exports, no `"use server"` directive).

- **DR-11 — extraction scope is `createDeck` + `saveCard` only.** `src/lib/deck-actions.ts` has
  seven exported functions and 28.1-PATTERNS.md correctly notes all seven use the same
  throw-based shape. But NAT-02's own text scopes this phase to "every read/write the **native
  v1** needs", and D-10 defines native v1 as sign up/in/out, dashboard, study sessions, manual
  add-a-word, habitat, plus basic account. `editCard`, `deleteCard`, `addWordToCard`,
  `saveImageCards`, `removeWordFromDeck` and `getSameLanguageDeckBackWords` back card
  editing/deletion, the wordlist-browse mode and the image-extract mode — the latter two are
  explicit programme-level deferrals in 28-CONTEXT.md. Those five stay unchanged throw-based
  server actions. This is scoping to the requirement's own words, not reducing it; if 28.3
  discovers native needs one of them, extracting it then is a small, well-precedented change
  because this plan establishes the pattern.

- **Core functions take an already-authenticated `userId`; they do NOT resolve the session
  themselves.** The two entry points legitimately differ in how they read the session — RSC
  pages and server actions use the `cache()`-wrapped `getSession()`/`getSessionFresh()` from
  `src/lib/auth-session.ts`, while route handlers call `auth.api.getSession` raw (four
  independent confirmations of that convention in the existing routes). Baking one of them into
  the core would force the other entry point into the wrong session semantics. Auth stays at the
  boundary; the core owns ownership + business logic + writes.

- **`revalidatePath("/dashboard")` stays in the server action, never in the core.** It is a
  Next.js Server Component cache concern with no meaning for a native client
  (28.1-PATTERNS.md Group G says drop it on the route-handler path).
</planner_decisions>

Module-level constants at lines 15-22:

`ALLOWED_LANGUAGES = new Set(["fr", "es", "en"])` (the SEC-06 allow-list).

`createDeck(language: string)` — lines 32-55, in this exact order:
1. `if (!ALLOWED_LANGUAGES.has(language)) throw new Error("Invalid language");`
2. `const session = await auth.api.getSession({ headers: await headers() }); if (!session) throw new Error("Unauthorized");`
3. `const userId = session.user.id as UserId;`
4. `db.select({ count: count() }).from(decks).where(and(eq(decks.userId, userId), eq(decks.language, language)))`
5. `const n = Number(existing[0]?.count ?? 0) + 1;` `const label = LANGUAGE_LABELS[language] ?? language;` `const name = \`${label} #${n}\`;`
6. `const id = crypto.randomUUID() as DeckId;`
7. `await db.insert(decks).values({ id, userId, language, name });`
8. `revalidatePath("/dashboard");`
9. `return { id, name, language };`

**The language check runs BEFORE the session check.** Preserve that ordering exactly — an
unauthenticated caller passing an invalid language must still get `"Invalid language"`, not
`"Unauthorized"`.

`saveCard(deckId, front, back, source)` — lines 65-89, in this exact order:
1. session → `throw new Error("Unauthorized")` if absent
2. `const userId = session.user.id as UserId;`
3. `db.select().from(decks).where(eq(decks.id, deckId as DeckId))` then
   `if (!deck || deck.userId !== userId) throw new Error("Forbidden");`
4. `const id = crypto.randomUUID() as CardId;`
5. `await db.insert(cards).values({ id, deckId: deckId as DeckId, front, back, source });`
6. `revalidatePath("/dashboard");` then `return { id };`

Note step 3 uses a plain `SELECT ... WHERE id = ?` then compares `deck.userId` in JS. The
stronger, already-used-elsewhere form is the combined-WHERE gate
`where(and(eq(decks.id, ...), eq(decks.userId, userId)))` — see `saveImageCards` lines 272-276
("IN-01: a single atomic gate that never returns a foreign-user deck row") and
`getSameLanguageDeckBackWords` line 208. Adopt the combined-WHERE form in `saveCardCore`; it is
strictly safer, returns the same `"Forbidden"` outcome for the same inputs, and matches the
convention every other ownership check in this repo already uses.

`src/lib/deck-actions.test.ts` — 33 `it()` blocks across 8 `describe()` groups, using
`vi.hoisted()` chain mocks for `select`/`insert`/`update`/`delete`, and mocking `next/headers`,
`next/cache` (`revalidatePath`) and `@/lib/auth`. The `createDeck` group (lines 121-185) and the
`saveCard` group (lines 186-222) are the contract this plan must not break. Because those mocks
target `@/db` and `@/lib/auth` — which `src/lib/core/decks.ts` will also import — they keep
working through the delegation without any test edit.

The error convention to return is `CoreResult<T>` from `@leocards/domain/contracts`, created in
plan 28.1-03: `{ ok: true; data: T } | { ok: false; code: CoreErrorCode }` with
`CoreErrorCode = "unauthorized" | "forbidden" | "invalid" | "rate-limited"`.
