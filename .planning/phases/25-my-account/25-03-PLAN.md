<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| edit form → authClient.updateUser / requestEmailChange | name + candidate email cross to the (server-authorized) mutations |
| server pending state → pending banner | server-derived pendingEmail prop renders; client never fabricates it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-03-A | Tampering | name update (IDOR) | mitigate | authClient.updateUser hits better-auth /update-user which re-derives the session user; no client-supplied id |
| T-25-03-B | Info Disclosure | email-in-use error surfaced in UI | accept | Renders the honest error the action returns (see T-25-01-I); deliberate low-stakes tradeoff |
| T-25-03-C | Tampering | pending banner (client fabrication) | mitigate | Persistent banner is driven by the server-read `pendingEmail` prop (getPendingEmailChange), not client state |
| T-25-03-D | Info Disclosure | stale-vs-new email display | mitigate | The Email row renders the ACTIVE (old) address prop while a change is pending; the new address never becomes the sign-in identity until verified (D-07) |
</threat_model>
