## Spacing Scale

Declared values (multiples of 4, per the project's established scale):

| Token | Value | Usage in This Phase |
|-------|-------|---------------------|
| xs | 4px | Icon-to-text gaps inside small rows (chevron offset, Trash2-to-text gap) |
| sm | 8px | Label-to-value gaps, chip/gap spacing |
| md | 16px | Save/Cancel button stack gap (`gap-4`), field-to-field gaps inside forms |
| lg | 20px | Card internal padding (all cards this phase); gap between stacked page sections |
| xl | 32px | Extra top margin isolating the Delete-account row from the Log out card above it |
| 2xl | 48px | Page bottom padding |
| — | 44px | **Touch-target floor — see Exceptions** |

**Exceptions (inherited control heights — not new tokens, reused verbatim from existing atoms):**
- `TField` height: 48px (`h-12`) — `src/components/daybreak/t-field.tsx`.
- `TBtn` height: 50px (`h-[50px]`) — `src/components/daybreak/t-btn.tsx`.
- shadcn `Button` (outline/destructive variants) height: must be explicitly set to **44px (`h-11`)** — the component's own default sizes (`size="default"` = 32px, up to `size="lg"` = 36px) are all **below the 44px floor** and must never be used bare. Every `Button` used in this phase carries an explicit `h-11` override, matching `card-edit-dialog.tsx`'s exact precedent (`className="w-full h-11"`).
- Form field gap: **15px** (`gap-[15px]`) — matches the exact value used by every existing auth form (`signup/page.tsx`, `forgot-password/page.tsx`, `reset-password/page.tsx`), reused here for the change-password fields.
- Chrome-row gap: **14px** (`gap-[14px]`) — within the Daybreak README's documented 11–16px in-group rhythm; deliberate (not rounded to `md`/16px) so the back button + title cluster reads as one unit, mirroring the habitat chrome this page's back-button pattern comes from (D-02).
- "Change password" collapsed-row padding: **18px 20px** — pre-existing Daybreak row-padding pattern, `src/components/review-list.tsx:614`.
- **44px is a hard floor, not a target to round down from.** A pre-existing e2e assertion (`box?.height` / `box?.width` `>= 44`) caught a real 38px→44px regression in Phase 23. Two controls in this phase are **locked at a smaller visual size by decision** (D-01's 36px header glyph; the back button's 40px visual, mirroring `HBack`) — both use the documented workaround: **the small visual sits inside a 44×44 transparent/invisible hit-area wrapper.** See §Accessibility Contract → "Small-Target Wrapper" pattern. Never ship the visual box itself as the clickable element when it's under 44px.

## Page Chrome & Layout

### Visual hierarchy (explicit intent)
`/account` is a **deliberately flat, sequential-scan utility page** — there is no single dominant focal point (consistent with D-02's declined avatar/identity block). The chrome row (back button + "My Account" display title) is the entry anchor; below it, visual weight *descends* in D-03's fixed order: the Account Details card is the first and heaviest block, Change Password and Sign out are progressively quieter cards, and the Delete-account text row at the very bottom is intentionally the lightest element on the page. Executors must not introduce a hero, illustration, or emphasized block that competes with this quiet top-to-bottom decay.

### Route & session
`src/app/(protected)/account/page.tsx` — inherits the `(protected)/layout.tsx` session gate (redirects to `/login` if unauthenticated). Fetches `session.user` (already contains `name`, `email`, `createdAt`, `nativeLanguage` — the `nativeLanguage` `additionalField` is already configured in `src/lib/auth.ts`) via `auth.api.getSession({ headers: await headers() })`, matching the exact pattern in `dashboard/page.tsx` / `habitat/page.tsx`. No new DB query needed for the details card's 4 fields.

### RSC-first framing (perf constraint, Phase 17 in flight)
Nearly every element on this page is directly interactive (edit toggle, accordion, two mutations, a two-step confirm) — unlike Dashboard/Habitat, there isn't a large static subtree to keep server-rendered below the fold. "RSC-first" here concretely means:
1. Session + user data fetch happens **once, server-side**, in `page.tsx` — never re-fetched client-side on mount.
2. The page title and outer chrome markup stay server-rendered where they carry no interactivity.
3. **Zero new client-side libraries** — no `motion/react`, no new animation dependency. All motion is the existing CSS-keyframe convention (paired with `prefers-reduced-motion` overrides, per every prior phase's pattern in `globals.css`).
4. Each interactive section is its **own small client component**, not one monolithic client page — keeps future edits to one section from forcing full-page client re-renders, and keeps bundle boundaries legible.
5. `/account` is not one of the four Phase 17 key routes, but any new shared-chunk weight shows up everywhere — hence zero new deps is non-negotiable, not a nice-to-have.

## Section 1 — Account Details Card (D-05, D-06, D-07)

### §1a. View mode
`Card` (radius 22, `#F0E3CF` border, `--db-card-shadow`), 20px internal padding, `data-testid="account-details-card"`.

- Top row: nothing on the left (no eyebrow label — the page title + the card being first already establishes context; adding "ACCOUNT DETAILS" text would be redundant per D-12's own "no gold-plating" spirit applied consistently); "Edit" link right-aligned, `text-[13px] font-bold text-[var(--db-link)]`, wrapped in the Small-Target Wrapper (44px hit area), `data-testid="account-edit-btn"`.
- 4 rows, each: `flex items-center justify-between py-3 border-b border-[#F0E3CF] last:border-b-0` — label left (`text-[13px] font-semibold text-muted-foreground`), value right (`text-[15px] font-semibold text-foreground truncate ml-4`).
  1. **Name** — `user.name`
  2. **Email** — `user.email` (the currently-*active* email; stays the OLD address even while a change is pending, per D-07)
  3. **Member since** — `user.createdAt`, formatted `Intl.DateTimeFormat("en-US", { month: "long", year: "numeric" })` → e.g. **"July 2026"**. Computed server-side in `page.tsx` (avoids a client-side `toLocaleDateString` hydration-mismatch risk).
  4. **I speak** — `user.nativeLanguage` mapped through the existing `LANGUAGE_LABELS` dict (`en`→English, `fr`→French, `es`→Spanish, already defined in `dashboard/page.tsx`) → plain text, e.g. **"English"**. No `LangChip` — keeping it plain text signals non-interactivity (D-05: display-only) rather than implying an editable chip control.

### §1b. Edit mode
Triggered by "Edit." Same `Card`, content swaps **instantly** (no transition — matches `card-edit-dialog.tsx`'s exact view/edit-equivalent swap precedent).

```
TField "Name"   — value=user.name,  type=text
TField "Email"  — value=user.email, type=email, hint="Changing this sends a confirmation link to the new address."
[Member since / I speak — SAME static row styling as view mode, unchanged, positioned below the two fields]
TBtn "Save changes"        (full width, isPending spinner)
Button variant=outline h-11 w-full "Discard changes"
```

- Field gap: `gap-[15px]` (matches auth-form precedent exactly).
- Validation (zod, client-side, mirrors `signup/page.tsx` verbatim):
  - `name: z.string().min(1, "Name is required")`
  - `email: z.string().email("Please enter a valid email")`
- Server error (email already taken by another account): inline under the Email field — **"That email is already in use."**
- Generic fallback (any other save failure): inline text above the buttons, `text-sm text-destructive` — **"Couldn't save your changes. Try again."** (matches the `Couldn't {verb}. Try again.` formula used 2× more below, for a consistent through-line).
- **Member since / I speak are never editable** (D-06) — rendered read-only in both modes, no input affordance.
- Save/Cancel stack full-width, `TBtn` first then outline `Button`, `flex flex-col gap-4` — matches `card-edit-dialog.tsx` 1:1.
- `data-testid`: `account-name-field`, `account-email-field`, `account-save-btn`, `account-cancel-btn`.
- **D-04 does NOT cover this form.** The dirty-form back guard is scoped to the change-password fields only (per the decision's literal text and the Landmines note in `25-CONTEXT.md`). Navigating back mid-edit here silently discards, same as tapping "Discard changes." This asymmetry is intentional, not an oversight — flagging it here so it isn't "fixed" into scope creep later.

### §1c. Email-pending-verification state
On Save, if the email value changed: the name change (if any) applies immediately; the email change does **not** apply immediately (D-07 — better-auth's default `changeEmail` behavior applies instantly when `emailVerified=false`, which is every LeoCards user today, so this must be custom-wired, not the library default). The card returns to **view mode**, Email row still shows the OLD address, and this banner appears directly beneath the details card:

```
ACBanner kind="ok" data-testid="account-email-pending-banner"
  "Verification sent to {newEmail}"                                          (bold line)
  "The change applies once you click the link. Your current email stays     (regular line)
   active until then."
  "Didn't get it? Resend email."   ← "Resend email" is the Small-Target-Wrapped
                                       link, data-testid="account-email-resend-btn"
```

- Editing again while a change is pending: the Email `TField` pre-fills with the **current (old, still-active)** address; saving again **replaces** the pending request (new token, new "sent to" target) — not additive.
- This banner **must be driven by server-persisted pending state** (read in `page.tsx`, not local component state) — D-07's flow spans sessions/devices (the confirmation click happens in a different browser context). The concrete storage mechanism (better-auth hook vs. a custom `verification`-table token) is a planner/researcher decision per D-07's own discretion note — out of this UI spec's scope, but the UI contract above is fixed regardless of which mechanism is chosen.
- **Verification-link landing state** (Claude's Discretion, resolved here): rather than building a dedicated confirmation screen, the verification link should point at a route that verifies server-side and redirects to `/account?verified=success` or `/account?verified=expired`. `page.tsx` reads that query param and renders a **one-time** `ACBanner` at the very top of the content (above the details card):
  - `?verified=success` → `ACBanner kind="ok"` — **"Email verified — you're all set."**
  - `?verified=expired` → `ACBanner kind="error"` — **"That verification link has expired. Edit your email again to send a new one."**
  - `data-testid="account-verify-result-banner"`. Transient by nature of being query-param-driven — no dismiss button needed; it stops appearing once the user navigates without that param.
  - Rationale: reuses the existing `ACBanner` primitive and the already-built `/account` page instead of a net-new screen; satisfies the README's "recovery everywhere, never a dead end" principle cheaply.

### §1d. Loading / disabled
`TBtn isPending` shows the spinner and disables; both `TField`s get `disabled` (existing prop, matches `card-edit-dialog.tsx`). No initial-page-load shimmer anywhere on this card — data is fully resolved server-side before first paint (matches the `dashboard`/`habitat` RSC pattern exactly; do not add a `DaybreakShimmer` here, there is nothing to placeholder).

## Section 5 — Dirty-form back guard (D-04)

Scope: **only** the change-password fields, **only** the in-page `AccountBack` control (not the details-edit form, not the browser back button — see the scope notes in §1b and §2b).

**State:** `AccountDirtyProvider` (`src/components/account-dirty-context.tsx`) holds `{ passwordDirty, setPasswordDirty }`. `ChangePasswordCard` calls `setPasswordDirty(currentPassword !== "" || newPassword !== "" || confirmNewPassword !== "")` on every field change (and resets to `false` on successful save or manual collapse-with-empty-fields). `AccountBack` reads `passwordDirty` via `useAccountDirty()`.

**On `AccountBack` click while `passwordDirty === true`:** intercept navigation (`preventDefault`/don't route), open a `Dialog`:

```
Dialog (max-w-md, rounded-[22px], border border-[#F0E3CF], bg-[var(--background)], showCloseButton={false})
  data-testid="account-discard-dialog"
  Title: "Discard changes?"
  Body:  "Your password changes haven't been saved."
  TBtn                        "Stay"    data-testid="account-discard-stay-btn"   (primary — top, the encouraged path)
  Button variant=outline h-11 "Leave"   data-testid="account-discard-leave-btn"  (secondary — bottom)
```

- "Stay" closes the dialog, fields remain intact, user stays on `/account`.
- "Leave" closes the dialog and completes the original navigation to `/dashboard`, discarding the unsaved password text.
- `passwordDirty === false`: `AccountBack` navigates immediately, no dialog.
- Exact styling override matches `card-edit-dialog.tsx`'s `DialogContent` className verbatim, for visual-family consistency with the one other dialog already in the app.
